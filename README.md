# BendKV — формально верифицированное Redis-совместимое KV-хранилище на Bend2 (PoC)

Цель — оценить, можно ли переписать популярную open-source БД (SQLite, Redis и т. п.)
на [Bend2](https://github.com/bendlang/bend) так, чтобы получить формально
верифицированную БД или кэш, и проверить это на небольшом PoC.

Окружение: Bend 2.0.35 (`bendlang/bend` @ `1cce499`; старый `HigherOrderCO/Bend2`
теперь только указывает на новый репозиторий), Lean 4.34.0 для `--verdict`, clang 19,
эталон — Redis 7.0.15.

In English: [docs/FINDINGS.md](docs/FINDINGS.md) (what the work found),
[docs/DIRECTIONS.md](docs/DIRECTIONS.md) (verified databases, compilers, parallelism, and
where the work goes next), [tools/README.md](tools/README.md) (how it was measured).

## Короткий вывод

- **SQLite на Bend2 сейчас переписать нереалистично.** Мешает не только объём
  (~220 тыс. строк C), но и пробелы платформы: нет 64-битных целых и double, нет `fsync`,
  `rename`, блокировок и записи по смещению, файлы ограничены U32 (4 ГиБ), строки —
  связные списки. Даже лучшие верифицированные хранилища (IronKV, VeriBetrKV на Dafny,
  FSCQ и DaisyNFS на Coq) — это человеко-годы работы, и верифицированного SQL-движка
  уровня SQLite не существует.
- **Redis реалистичен как «верифицированное ядро + проверенная тестами оболочка»** — и PoC
  это подтверждает. Получилось ~710 строк кода ядра, ~450 строк разбиения пачки по
  шардам и слияния их ответов, ~210 строк журнала (AOF) и ~4 300 строк доказательств,
  написанных руками, плюс ~2 500 строк 16-ричных разборов трая, которые пишет генератор,
  и 45 законов (без комментариев и пустых строк). Bend проверяет их примерно за
  секунду, а ядро BendTT (его корректность доказана в Lean) — за ~3 с. Доказано и
  восстановление после перезапуска: сервер с журналом (AOF в формате Redis) поднимает из
  файла ровно ту базу, которую держал, а из файла, оборванного сбоем на любом байте, —
  базу после некоторого префикса своих команд; с шардами — каждый шард из своего файла. На ~266 тыс. случайных команд ответы байт в байт совпали с настоящим
  Redis 7; версии с траем на 16 детей прошли ещё ~300 тыс., из них текущая — ~96 тыс.
- **Цена — скорость и память, и большую часть её удалось снять.** На исходном Bend при
  упоре в CPU (конвейер 16) BendKV был в 7–21 раз медленнее Redis, а памяти на ключ ему
  требовалось в ~5 раз больше. Причина — модель памяти рантайма Bend, а не верификация.
  Девятнадцать патчей к компилятору Bend ([`bend-patches/`](bend-patches/): ленивое
  запечатывание счётчиков, упакованные строки с байтовым вводом-выводом, заимствующее
  чтение, нативные строковые операции, перестройка узла на месте, страницы по 2 МиБ для
  кучи, выбор поля по цифре без таблицы переходов, строка из одного куска без узла,
  подсказка процессору о предвыборке, несколько ядер: циклы событий на своих потоках,
  отправка в несколько каналов одним шагом, отправка по TCP через поток-писатель;
  `epoll` вместо `select`; байтовый файловый ввод-вывод с `fsync` и приём из канала без
  ожидания — для журнала; `code_at` коротких строк в терме, отправки, которые цикл делит
  с писателем, и эффекты-пары `Chan.call` и `TCP.post_recv_raw`; отправки самим циклом,
  пока он успевает; чтение строки по индексу без среза; `IO`, скомпилированный в прямые
  продолжения) и переделка горячих путей BendKV дали следующее:
  - по бенчмаркам самого Redis (его спецификации для `memtier_benchmark`, раздел 7.15
    PERFORMANCE.md) на миллионе ключей, сервер на одном ядре: загрузка со значениями по
    100 байт — 1,39 пропускной способности Redis, GET с конвейером 10 — 1,26, с
    конвейером 100 — 1,36, INCR — 1,00, GET без конвейера — 0,90;
  - на двух ядрах, когда ответы отправляет поток-писатель (раздел 7.16): загрузка —
    **1,94** от Redis, GET с конвейером 10 — **1,61**, с конвейером 100 — 1,39, INCR —
    1,27, GET без конвейера — 1,11. Redis с `io-threads 2` на тех же ядрах — 0,99–1,22 от
    себя однопоточного. Базу можно разделить на шарды по ядрам (`./bendkv PORT N`); на
    двух ядрах это окупается только без конвейера (1,19), а с конвейером один цикл с
    писателем быстрее, потому что термы, переходящие между ядрами, дороже параллельной
    работы с картой;
  - с `epoll` вместо `select` (одиннадцатый патч, раздел 7.17) GET без конвейера на тех
    же двух ядрах — **1,27** от Redis (с `select` в той же серии — 1,15), время ядра ОС
    на запрос на 30% меньше. На трёх ядрах сервера один шард с писателем даёт 897 тыс.
    GET/с с конвейером 10 — 2,06 от Redis с тремя io-threads. Шарды теперь возвращают
    ответы байтами (+33% на двух шардах), но на трёх ядрах с конвейером один шард с
    писателем всё ещё быстрее (три шарда — 816 тыс.). Сборка с профилем (`make pgo`)
    добавляет 1–4%;
  - при конвейере 16 на заполненной базе из 100 тыс. ключей (`redis-benchmark` со
    значениями по 3 байта: лучший для BendKV случай) BendKV быстрее Redis:
    **GET 1,62** его пропускной способности, **SET 1,82**, **INCR 1,45** (было 0,08–0,14).
    На миллионе ключей — 1,65, 1,80 и 1,17. Так стало с подсказками процессору по пачке:
    до них было 1,17–1,21, 1,10–1,15 и 0,95–0,96 на 100 тыс. ключей и 1,02–1,14,
    1,06–1,24 и 1,04–1,12 на миллионе (по сериям двух дней на разных ВМ). На тысяче
    ключей, где всё и так в кэше, — 1,09, 1,13 и 0,95;
  - без подсказок инструкций на запрос меньше, чем у Redis: на GET 3 280 против 3 549,
    на SET 3 985 против 4 773, на PING 2 172 против 2 438; на INCR — 4 209 против 3 948.
    Промахов мимо L2 на GET и SET тоже меньше: 2,4 и 2,8 против 2,7 и 3,3. Подсказки
    добавляют 14–17% инструкций (GET 3 834), зато прячут ~85% ожидания памяти;
  - без конвейера BendKV держит 118–132% пропускной способности Redis;
  - памяти на ключ нужно вдвое меньше, чем Redis: ~63 байта против ~128 на ~950 тыс.
    ключей (60 МБ RSS против 121 МБ) при значениях по 3 байта; при 100 байтах — 192
    байта против 221 (0,87 от Redis), и чтение её не прибавляет (до раздела 7.25
    PERFORMANCE.md первый GET значения добавлял ему 8 байт);
  - SET значения 1 МБ — 4,4 мс, GET — 1,4 мс (у Redis ~1 мс);
  - с журналом (AOF, раздел 7.19) при `everysec`, умолчании обоих, BendKV с конвейером 16
    быстрее Redis с тем же журналом: SET в **1,96** раза, INCR в 1,76, GET в 1,74; при
    `always` — в 1,15–1,73. Без конвейера при `always` они равны: оба упираются в
    `fdatasync` и оба объединяют запросы клиентов в одну синхронизацию. Журнал из
    миллиона SET BendKV читает за 1,62 с, Redis — за 1,24 с;
  - журнал есть и на шардах, по файлу на шард (раздел 7.21). По спецификациям Redis на
    двух ядрах сервера, у всех журнал с `everysec`: один шард — 1,17–1,87 от Redis, два
    шарда — 1,02–1,71 (загрузка миллиона ключей — 1,87 и 1,71). Без конвейера два шарда
    с журналами быстрее одного в 1,3–1,5 раза. Два шарда восстанавливают журнал из
    миллиона SET одновременно, каждый свой файл, за 0,44 с (один шард — 1,05 с, Redis —
    1,38 с в той же серии);
  - после пяти шагов по разбивке профиля (раздел 7.23 PERFORMANCE.md: разбор RESP
    дешевле, длинные чтения окнами, цикл делит отправки с писателем, эффекты парами;
    подсказки на всю группу актора сделаны, измерены и убраны) инструкций на запрос на
    8–9% меньше при конвейере 16, на 19% без конвейера и на 44–54% при конвейере 100. По
    спецификациям Redis на двух ядрах: загрузка — **1,93** от Redis, GET с конвейером 10 —
    1,46, без конвейера — **1,37**, с конвейером 100 — **1,69**, INCR — 1,43 (в той же
    серии до шагов: 1,73, 1,43, 1,23, 1,35 и 1,39). Без конвейера под `redis-benchmark`
    (один поток клиента) Redis был быстрее: BendKV с писателем — ~0,80 от него;
  - после ещё трёх шагов (раздел 7.24 PERFORMANCE.md) этот разрыв закрыт: цикл
    отправляет ответы сам, пока успевает за сокетами, и без конвейера под
    `redis-benchmark` BendKV — 0,93–1,05 от Redis на GET и 0,90–0,98 на SET (три серии).
    Запрос разбирается сразу в команду вместе с хешем ключа и доказательством, что хеш
    подходит, а `IO` компилируется в прямые продолжения: вместе это ещё 10–14% инструкций
    (GET 2 969, SET 3 534, INCR 3 830 при конвейере 16), но по времени меньше шума — ядро
    теперь около половины CPU запроса. По спецификациям Redis на двух ядрах: загрузка —
    **2,25** от Redis, GET с конвейером 10 — 1,62, без конвейера — 1,37, с конвейером
    100 — **1,95**, INCR — 1,39; при конвейере 16 на одном ядре — **1,86, 1,83 и 1,54**
    на GET, SET и INCR.

  Куда смотреть, показывал профиль по времени, снятый сэмплированием по таймеру
  ([`tools/sprof.c`](tools/sprof.c)). Строки до 6 байт лежат прямо в слове терма, и
  значение `"xxx"` не стоит ни одного промаха; строка из одного куска — сам буфер, и
  сравнение ключа стоит один промах, как у Redis. Перед каждой пачкой BendKV проходит пути
  всех её ключей уровень за уровнем, только начиная загружать следующий уровень
  (`Mem.prefetch`), и промахи разных ключей перекрываются; закон `batch_hints` доказывает,
  что это ничего не меняет. На одном ядре медленнее Redis BendKV там, где пачек нет: GET
  без конвейера (0,90, путь одной команды через соединение, канал и актор дороже, чем у
  Redis) и INCR на маленькой базе (0,95 на тысяче ключей). Подробный разбор и план — в
  [PERFORMANCE.md](PERFORMANCE.md).
- **Что значит «верифицирован».** Доказано, что *исходный код* на Bend удовлетворяет
  законам. Компилятор Bend (по README проекта — на 99% написан ИИ и не прошёл аудит),
  его C-рантайм, clang и ОС остаются в доверенной базе. Это не end-to-end-верификация
  в духе CompCert/seL4.
- Важно для этого репозитория: Bend2 **больше не использует HVM** — у него собственный
  рантайм BendRT (C/CUDA/Metal/JS). PoC с HVM4 не связан.

## Что сделано: BendKV

Redis-совместимый сервер (RESP2) в памяти. Работают `redis-cli` и `redis-benchmark`.

```
server.bend  TCP, соединения, акторы шардов, файл журнала   ─┐ не верифицирован (@unsafe-циклы),
resp.bend    разбор RESP2 и сериализация ответов            ─┘ проверен тестами
aof.bend     журнал: эффекты пачки, запись, чтение, повтор  ─┐ верифицирован:
wire.bend    слияние ответов шардов байтами                  │ LAWS.bend + PROOF.bend
shard.bend   пачка → части по шардам и ответы обратно        │
batch.bend   пачка с подсказками процессору                  │
redis.bend   семантика команд: exec(cmd, db) → (reply, db')  │
map.bend     хеш-трай со строковыми ключами                 ─┘
```

**Команды:** PING, ECHO, GET, SET, SETNX, GETSET, DEL/UNLINK, EXISTS, INCR, DECR, INCRBY,
DECRBY, APPEND, STRLEN, MGET, MSET, DBSIZE, FLUSHALL/FLUSHDB, KEYS (glob с `*` и `?`).
COMMAND, CONFIG и SELECT — заглушки, чтобы `redis-cli` и `redis-benchmark` не спотыкались.
Поддержаны конвейеризация, частичные пакеты, inline-команды (можно работать через `nc`)
и бинарно-безопасные значения.

**Устройство.** Команды исполняет актор базы данных. Как и в Redis, все команды
выполняются последовательно, в порядке поступления. Соединения разбирают запросы
и отправляют их актору пачками через каналы. Актор забирает разом все пачки, которые его
ждут (`Chan.drain`), исполняет их по очереди и отвечает всем одним шагом
(`Chan.send_all`). Ответы отдаются потоку-писателю (`TCP.post`), и цикл не ждёт
системного вызова `send`; для одного шарда писатель включается сам, когда процессу
доступны хотя бы два ядра (на одном он только отнимал бы время у цикла). С `./bendkv PORT N` база делится на
N шардов по младшей цифре хеша ключа, каждый шард — актор на своём ядре. Соединение режет
пачку на части по шардам и отдаёт их всем шардам одним шагом (`Chan.send_all`), поэтому
шарды исполняют пачки всех соединений в одном порядке: это то же, что исполнить их по
очереди, и пачка атомарна, даже MSET по ключам разных шардов (раздел 7.16
PERFORMANCE.md). Шард сам кодирует ответы своих команд, и соединение сливает уже байты
(`wire.bend`, раздел 7.17). Ответы шардов по умолчанию отправляет сам цикл: писатель
окупается, только когда ему есть отдельное ядро (`./bendkv PORT N post` включает
писателей). Доказано, что на любые пачки такой сервер отвечает так же, как однопоточный
(законы о шардах ниже).

**Журнал (AOF).** С `./bendkv PORT N post|send FILE [always|everysec|no]` актор исполняет
пачку через `exec_log` (`aof.bend`, после подсказок процессору, как обычно): кроме ответов и базы она даёт эффекты — что пачка
сделала, в виде команд. Чтение не даёт ничего, SET, SETNX, GETSET, APPEND, DEL, MSET и
FLUSHALL — себя, а INCRBY — SET нового значения (так Redis пишет INCRBYFLOAT): при чтении
журнала ни одно число не разбирается из текста. Эффекты дописываются в файл до ответа
клиенту, в формате AOF самого Redis (массивы bulk-строк). Актор берёт запрос и вместе с
ним все, что пришли, пока он работал (`Chan.drain`), исполняет их пачки одну за другой,
пишет их эффекты одной записью, при `always` делает один `fsync` и отвечает всем сразу
(групповая фиксация, как в цикле Redis). При `everysec` (умолчание, как у Redis) файл
синхронизирует раз в секунду отдельное вычисление через свой дескриптор, при `no` — ОС.
При старте сервер читает файл и исполняет его записи на пустой базе. Если файл кончается
посреди записи (сбой во время `write`), он обрезается до последней целой записи, как в
Redis с `aof-load-truncated yes`, и доказано, что база тогда — та, что была после
некоторого префикса команд; что-то иное после записей — отказ стартовать, тоже как
в Redis. Файл, который есть, но не открывается (нет прав, ошибка ввода-вывода, нет
свободных дескрипторов), — тоже отказ: пустая база с дописыванием в старый файл
разошлась бы с ним. Неудавшийся `fsync` останавливает сервер и при `everysec`, как при
`always`: подтверждённые записи могли не попасть на диск, а ядро после такой ошибки
может выбросить грязные страницы, и следующий удачный `fsync` этого не покажет (Redis
в этом случае отвечает на записи ошибкой `MISCONF`, пока `fsync` снова не пройдёт).

С N шардами у каждого шарда свой файл (`FILE.0`, `FILE.1`, …; с одним шардом — сам
`FILE`, который загружает и Redis): актор шарда пишет эффекты своих частей пачек, со своей
групповой фиксацией и своим `fsync`, а при старте все шарды восстанавливают свои файлы
одновременно, каждый на своём цикле. Кусок FLUSHALL на шарде (`FlushAt`, очистка
поддерева одной цифры) пишется записью `FLUSHAT <цифра>`: её читает загрузчик журнала, а
не сетевой разбор, так что клиенты такой команды не видят. Файлы сервера с другим числом
шардов он не принимает: ключи разложены по шардам по их числу.

**Хранилище** — трай на 16 детей по 5 шестнадцатеричным цифрам хеша FNV-1a (2^20 бакетов).
Бакет — цепочка записей прямо в трае, на случай коллизий. Структура выбрана ради
доказуемости: не нужен порядок на ключах (как в деревьях поиска), а разные пути ведут в
разные узлы. Поэтому законы доказываются индукцией по глубине обхода. Для корректности хеш
может быть любым; хороший хеш лишь сокращает бакеты. Обходы идут по цифрам самого хеша,
каждая цифра вычисляется заранее и передаётся параметром. Чтение ключа (`get`) ищет в
бакете прямо в конце обхода и только одалживает базу: компилятор с патчем `borrow-reads`
удерживает найденное значение на месте, а не разделяет весь трай. GET сервера отвечает
копией значения, сделанной там же (`get_copy.at`): значение в базе остаётся
неразделённым, без ячейки-счётчика, и подсказки по пачке доходят до его байтов; доказано,
что копия и есть значение (`tget_kc_eq`). Запись перестраивает путь на месте. 16- и 256-кратные разборы в коде и в доказательствах пишет
`tools/gen_trie.py`.

### Что доказано (LAWS.bend)

Законы формулирует человек, доказательства (`PROOF.bend`) пишет и проверяет машина.

**Отображение (5 законов).** Это полная аксиоматизация конечного отображения: после любой
последовательности SET/DEL чтение любого ключа однозначно определено, значит, устаревших,
потерянных или «чужих» значений не бывает.
- `get_empty` — в пустой базе нет ключей;
- `get_set_same` — после SET ключ читается как записанное значение;
- `get_set_other` — SET не меняет никакой другой ключ;
- `get_del_same` — после DEL ключа нет;
- `get_del_other` — DEL не меняет никакой другой ключ.

**Ключи (2 закона).** `key_eq_true` и `key_eq_false`: сравнение ключей `str_eq` — это ровно
равенство строк. `str_eq` — это `String.eq` из Base (в C-рантайме с патчем — `memcmp` по
кускам); доказано, что оно совпадает с посимвольным сравнением, а доказательство спускается
по представлению до 32 битов `U32`.

**Команды (15 законов)** о функции `exec`, которую сервер и исполняет:
- `frame` — **ни одна команда не меняет ключ, который она не пишет**: SET/DEL/MSET/INCR/APPEND/…
  трогают только названные ключи, FLUSHALL — все. Доказано для всех 20 видов команд:
  17 клиентских и трёх внутренних, которыми шарды исполняют DBSIZE, KEYS и FLUSHALL
  (ниже);
- `reads_keep_db` — команды чтения (GET, EXISTS, MGET, STRLEN, KEYS, DBSIZE, PING, ECHO,
  ошибки) не меняют базу целиком;
- `get_after_set`, `get_missing` — GET после SET и GET отсутствующего ключа;
- `del_effect` — после DEL удалён каждый названный ключ (с повторами и в любом порядке);
  `del_one_count` — DEL одного ключа отвечает 1 или 0;
- `append_effect` — APPEND сохраняет «старое ++ новое» и отвечает новой длиной;
- `setnx_missing` и `setnx_present` — SETNX ставит отсутствующий ключ и не трогает
  существующий;
- `incr_missing` — INCR отсутствующего ключа сохраняет "1" и отвечает 1;
- `batch_step` и `batch_nil` — **пакет команд исполняется ровно как последовательность
  команд**. Это связывает законы об одной команде с тем, как сервер исполняет
  конвейеризированные пачки;
- `batch_hints` — **подсказки процессору ничего не меняют**: сервер исполняет пачку через
  `batch.bend`, который сначала начинает загружать в кэш пути её ключей, а потом исполняет
  команды с уже готовыми хешами их ключей, и это ровно `exec_all`, если хеши подходят
  командам (`fits`: хеш ключа для команды на одном ключе, любой для остальных);
- `exec_at` — команда, исполненная с подходящим хешем ключа (`exec.at`), — это сама
  команда: ключ хешируется один раз, а не дважды (для подсказок и в `exec`);
- `fit_hashes` — **хеши, с которыми соединение разбирает запросы, подходят их командам**:
  разборщик (`resp.bend`) строит каждый запрос как `B.Fit` — команду, её хеш и
  доказательство, что хеш подходит, — так что тайпчекер проверяет каждое место, где
  разборщик выбирает хеш; GET, SET и INCR берут хеш ключа прямо из буфера, остальные
  команды — по первому аргументу (по всем случаям общего разбора `R.parse_id` команды на
  одном ключе берут ключ из первого аргумента). Сервер раскладывает пачку `Fit` на
  команды и хеши (`B.fit_unzip`), и закон говорит, что они подходят друг другу.

**Шарды (4 закона)** о сервере с N шардами (`shard.bend`). История — это пачки, которые
сервер исполнил со старта; однопоточный сервер исполняет её на одной базе, шардированный —
на своих траях:
- `shard_hashes` и `unzip_parts` — часть пачки приходит на шард с хешами, которые
  подходят её командам (их посчитал `split`, чтобы выбрать шард), и `unzip` раскладывает
  её на команды и хеши, как это делает сервер;
- `shard_replies` — **после любой истории шардированный сервер отвечает на пачку так же,
  как однопоточный**: пачку режут на части по шардам (`split`), каждый шард исполняет свою
  часть на своём трае, ответы собирают обратно в порядке пачки (`merge`), и выходят ровно
  ответы `exec_all` на одной базе;
- `shard_holds` — после любой истории каждый ключ читается в своём шарде так же, как в
  единой базе.

Оба закона верны при любом числе шардов и для пачек из любых команд. Команда с
несколькими ключами (DEL, EXISTS, MGET, MSET) идёт на шарды кусками, по команде с одним
ключом на каждый ключ. DBSIZE, KEYS и FLUSHALL тоже идут кусками: по команде на каждую
цифру корня трая (`SizeAt`, `KeysAt`, `FlushAt`), каждая в шард, который держит поддерево
этой цифры. Доказательство исполняет историю по кускам, каждый на своём шарде, и держит
инвариант: под каждой цифрой корня шард этой цифры хранит ровно то же поддерево, что и
единая база. Кусок меняет только поддерево своей цифры, а его ответ и это поддерево после
него зависят только от этого поддерева до него. Остаётся показать, что куски команды,
исполненные друг за другом на единой базе, дают её ответ и её базу: DBSIZE — сумма
размеров поддеревьев, KEYS — их ключи подряд, FLUSHALL — очистка поддеревьев по очереди
(раздел 7.18 PERFORMANCE.md).

**Байты (3 закона).** С несколькими шардами каждый шард кодирует свои ответы сам, а
соединение сливает уже байты (`wire.bend`):
- `merge_bytes` — слияние байтами даёт ответы `merge` из `shard.bend`, каждый закодированный;
- `encodes_glue` — ответы, закодированные по одному и склеенные, — это пачка ответов,
  закодированная целиком (так отвечает однопоточный сервер);
- `shard_bytes` — поэтому **после любой истории шардированный сервер отправляет на любую
  пачку те же байты, что и однопоточный**.

**Коммутативность (5 законов).** Команды на разных ключах можно исполнять в любом
порядке. Ни одна команда не переносит значение с одного ключа на другой: ключ после
команды зависит только от того, как он читался до неё. Поэтому:
- `commute_reads` — после двух команд в любом порядке каждый ключ, который пишет не
  больше одной из них, читается одинаково;
- `commute_reply` — команда отвечает так же после другой, которая её не «тревожит»
  (`disturbs`: не пишет ни один ключ, который первая читает; для DBSIZE и KEYS — вообще
  ничего не пишет);
- `commute` — две команды, не тревожащие друг друга, дают те же ответы в любом порядке;
- `swap_replies` и `swap_reads` — **две соседние независимые команды пачки можно
  поменять местами**: их ответы меняются местами, остальная пачка отвечает так же
  (если в ней нет DBSIZE и KEYS), а в конце каждый ключ читается одинаково (это — при
  любой остальной пачке).

Законы говорят о том, как читаются ключи, а не о самом трае: два новых ключа одного
бакета лежат в порядке записи, и KEYS может перечислить их в другом порядке (Redis
порядка KEYS и не обещает). Поэтому DBSIZE и KEYS после перестановки исключены: для них
понадобился бы инвариант «в бакете нет повторов ключа».

**Персистентность (8 законов)** о журнале (`aof.bend`):
- `log_exec` — `exec_log` отвечает и меняет базу ровно как `exec_all`: с журналом сервер
  отвечает так же, как без него;
- `log_hints` — подсказки процессору и готовые хеши ключей и здесь ничего не меняют:
  актор исполняет пачку через `log_batch`, и с подходящими хешами это ровно `exec_log`;
- `log_replay` — эффекты пачки, исполненные на той базе, на которой исполнялась пачка,
  дают ту же базу, что и пачка;
- `log_args` — эффекты любой пачки, записанные строками запроса, разбираются обратно в
  себя, в том числе части пачки на шарде с кусками FLUSHALL (`FLUSHAT`);
- `aof_load` — **файл читается ровно как записанные в него записи**, и ничего не остаётся.
  Здесь доказан и десятичный круговой путь: длину, записанную `Nat.show`, разбор цифр
  читает обратно (через деление на 10 «шагами по десять» и топливо `Nat.show`);
- `recover` — **после любой истории пачек сервер восстанавливает из своего
  файла ровно ту базу, которую держал**, и после последней записи ничего не остаётся;
- `recover_cut` — **файл, оборванный сбоем на любом байте, восстанавливает базу, которую
  сервер держал после некоторого префикса своих команд**: ни одна команда не применена
  частично, ни одна — не по порядку и ни одна — после потерянной. Оборванная запись
  никогда не читается (строка числа без `\r\n`, bulk без байтов или без `\r\n`),
  записи — эффекты команд по порядку, а у команды не больше одного эффекта: первые k
  записей дают базу после первых j команд, для некоторого j;
- `load_cut` — прочитанные целые записи, записанные снова, вместе с остатком и есть
  оборванный файл: сервер отрезает ровно остаток, и в файле остаются целые записи.

**Журнал на шардах (3 закона).** История шарда — его часть каждой пачки истории сервера:
- `shard_recover` — **после любой истории каждый шард восстанавливает из своего файла ровно
  ту базу, которую держал**;
- `shard_restore` — поэтому каждый ключ читается в базе, которую восстановил его шард, так
  же, как в базе однопоточного сервера;
- `shard_recover_cut` — файл шарда, оборванный на любом байте, восстанавливает базу шарда
  после некоторого префикса его собственных команд. Файлы восстанавливаются каждый сам
  по себе, поэтому после сбоя команда, разрезанная на куски по шардам (MSET, DEL
  нескольких ключей, FLUSHALL), может сохраниться на одних шардах и потеряться на других;
  с `everysec` шарды теряют каждый свою последнюю секунду. Redis Cluster в той же
  ситуации такие команды просто запрещает (CROSSSLOT).

Законы журнала больше не требуют, чтобы пачка была клиентской: кусок FLUSHALL теперь тоже
пишется, и законы верны для любой пачки, а значит, и для истории каждого шарда.

Восемь мутаций журнала (не писать APPEND, писать в INCR не то число, сдвинуть цифру,
отнять у загрузчика топливо, записать лишний элемент в счётчик массива, считать `FlushAt`
клиентской, потерять пару MSET, не отрезать тело bulk-строки) ломают доказательство
ровно в том месте, которое они портят, как и пять мутаций журнала на шардах (цифра
`a` читается как `b`, кусок FLUSHALL не пишется, `FLUSHAT` читается как FLUSHALL, шард
пишет часть соседа, ключ ищется в файле шарда 0). Ещё две мутации загрузчика проходят все законы о
целом файле, и их ловят только законы об обрыве: bulk, оборванный посреди байтов,
читается как строка короче (значение, которого никто не писал), а запись, оборванная
между аргументами, — из того, что успело дойти (DEL a b c исполнился бы как DEL a b).

`bend PROOF.bend` → `ALL PROOFS CHECK` (~1 с); `bend PROOF.bend --verdict` → `ALL PROOFS CHECK`
(~3 с). Во втором случае каждое доказательство перепроверяет ядро BendTT, корректность
которого доказана в Lean. Трансляцию, которую читает ядро, можно выгрузить через
`bend PROOF.bend -o PROOF.bendtt` и прочитать формулировки законов глазами.

### Что проверено тестами

- **Дифференциальное тестирование против Redis 7.0.15** (`tests/diff_test.py`). Случайные
  потоки команд со случайными бинарными аргументами, конвейерами разной длины и ошибками
  арности/формата идут параллельно в BendKV и в настоящий Redis. 28 прогонов, ≈266 тыс.
  команд: все ответы идентичны. Исключение — известное и задокументированное: числа с 15+
  цифрами (BendKV отвечает ошибкой переполнения, Redis считает в int64). Тест распознаёт
  ровно этот случай.
- **Устойчивость** (`tests/robust_test.py`): запрос по одному байту (разбор через много
  TCP-чтений), значение 1 МБ, мусор в протоколе (ошибка и закрытие соединения, как в Redis),
  50 параллельных клиентов.
- `tests/smoke.bend` — сквозной прогон «буфер → разбор → исполнение → RESP» без сети.
- **Шарды.** `tests/shard_check.bend` сверяет split и merge с одним траем при 1, 2, 3, 4 и
  16 шардах на пачке из всех 16 команд. `make test` гоняет устойчивость и
  дифференциальный тест и для одного шарда, и для двух. `tests/concurrency_test.py`
  проверяет при многих клиентах три вещи: INCR не теряются, MSET по ключам разных шардов
  атомарен для MGET, а порядок записей одного клиента в разные шарды виден другим так же,
  как в Redis. Тест проходит на Redis и на BendKV с 1, 2 и 4 шардами. То же самое доказано
  (`shard_replies`) для любых пачек, в том числе для MSET по ключам разных шардов: если
  шарды исполняют пачки в одном порядке, ответы и база те же, что у однопоточного
  сервера.
- **Журнал.** `tests/aof_check.bend` пишет журнал пачки, читает и исполняет его и
  сверяет базу, а затем режет файл на каждой из его 806 длин и проверяет, что прочитанное
  и остаток вместе дают обрезок, а в остатке нет целой записи. `make test` гоняет весь
  набор и на сервере с журналом, с одним шардом и с двумя, а затем перезапускает каждый:
  случайный поток с FLUSHALL посередине плюс 20 тыс. ключей, перезапуск из файлов,
  сравнение всего пространства ключей (совпало: 20 411 ключей); дописанная обрезанная
  запись, перезапуск, который её отрезает, и снова то же пространство ключей; старт
  на файлах двух шардов с одним шардом и с четырьмя — отказ. `tests/aof_fail_test.py`
  ломает диск под журналом прокладкой `tests/fail_io.c` (`LD_PRELOAD`): файл, который
  есть, но не читается (у одного шарда, у одного из двух, другой раскладки), — отказ
  стартовать, файл не тронут; неудавшийся `fsync` при `everysec` и `always` — остановка. `redis-check-aof` из Redis 7 признаёт файлы BendKV корректными, Redis
  7.0.15 загружает журнал BendKV и получает те же данные, а BendKV загружает журнал,
  записанный Redis (с `SELECT`, именами команд в нижнем регистре и уже переписанным в SET
  GETSET).

- **Большие значения:** SET 1 МБ — 4,4 мс, GET — 1,4 мс у BendKV (было ~0,1 с) против
  ~1 мс у Redis.
- **Куда уходило время на исходном Bend** (callgrind, SET со случайными ключами): ≈50% —
  управление памятью. Это освобождение ячеек и 8-байтные ячейки-счётчики, которые
  компилятор создаёт при *построении* каждого значения «горячего» (где-либо разделяемого)
  типа. ≈20% — строки-списки и преобразование байтов, ≈11% — трай, ≈5% — разбор RESP.
  Само проверенное ядро — меньшая часть стоимости, основная — представление данных.
- **Что исправлено** (подробно — в [PERFORMANCE.md](PERFORMANCE.md)):
  - в Bend: ленивое запечатывание счётчиков; упакованные строки в C-рантайме;
    `TCP.recv_raw`/`send_raw`; заимствующее чтение (поле одолженного значения удерживается
    на месте, а не делает владельцем всё значение); нативные `++`, `length`, `eq`, `take`,
    `drop`, `hash`, `code_at`, `find`, `slice` и `Nat.show` над упакованными строками;
    литералы и цифры, которые пишутся прямо в запас буфера ответа; строки до 6 байт прямо
    в слове терма; перестройка узла на месте (через вызов сохраняется узел, а не поля);
    страницы по 2 МиБ для кучи; выбор поля узла по цифре одной загрузкой, без таблицы
    переходов и с одним продолжением вместо шестнадцати; строка из одного куска как сам
    терм буфера, без узла; подсказка процессору `Mem.prefetch`; `IO` в прямых
    продолжениях (блок `do` вызывает эффекты прямо, без замыканий `IO.bind`);
  - в BendKV: ввод-вывод буферами; трай на 16 детей; чтение без разделения базы; разбор
    запросов по индексу сразу в команду с хешем ключа; ответ, собранный с конца в один
    буфер; выбор команды по длине имени; разбор числа для INCR по индексу, без разборки
    строки; подсказки по пачке: пути всех ключей пачки загружаются уровень за уровнем до
    её исполнения.

  Аллокаций на SET стало 62 вместо 392, на GET — 35 вместо 305.

### Граница доверия

Доказательства покрывают `map.bend`, `redis.bend`, `batch.bend`, `shard.bend`, `wire.bend`,
`aof.bend` и сами законы. На доверии остаются:
1. **Компилятор и рантайм Bend.** `U32` в теории — вектор из 32 битов (`Word(32n)`),
   в рантайме — машинное u32; `Nat` в теории унарный, в рантайме — 64-битное слово
   с аварийной остановкой после 2^48−1; `String` в теории — список, а в C-рантайме
   с патчем — цепочка байтовых буферов, а `String.eq`, `String.hash` и другие операции над
   ней — функции на C. Соответствие рантайма определениям не доказано. Сервер собирается
   Bend с двадцатью патчами из [`bend-patches/`](bend-patches/). Они тоже в доверенной
   базе: проверены набором тестов Bend и дифференциальными тестами против Redis, но не
   доказаны. Сюда же относятся циклы событий на нескольких потоках, `epoll`, атомарность
   `Chan.send_all`, поток-писатель и отправки, которые цикл делит с ним, файловые
   `write`/`read`/`fdatasync`/`ftruncate`, `Chan.drain`, `Chan.call` и
   `TCP.post_recv_raw`, нативные `String.dec_line_at` и `hash_at` и перевод `IO` в
   продолжения в компиляторе.
2. **`resp.bend` и `server.bend`** — протокол и сеть; они проверены только тестами. Сюда
   же относятся пересылка частей пачки шардам и сбор их ответов в `server.bend` (`sends`,
   `part_req` с `S.unzip`, `collect`): законы говорят о `split` и о слиянии ответов и
   байтов, а не о каналах. На доверии и то, что шард кодирует свои ответы `W.outs`, а
   соединение собирает их по шардам в том же порядке, что `W.store_of`.
   С журналом на доверии и то, что сервер дописывает в файл именно эффекты каждой пачки
   (группа пачек пишется одной записью: `encode` склейки — склейка `encode`, это
   доказано в `enc_cat`). Когда файл кончается посреди записи, доказано, какую базу
   сервер поднимает и до какого байта режет файл (`recover_cut`, `load_cut`); на
   доверии лишь решение резать: что остаток — начало записи, а не мусор, сервер узнаёт
   сетевым разбором `resp.bend` (`cut_short`). Для оборванного файла ошибка там может
   только помешать старту, но не изменить базу. С шардами на доверии и то, что актор
   шарда пишет в свой файл эффекты именно своих частей пачек (`part_req`), что файл шарда
   s — это `FILE.s`, и отказ на файлах другой раскладки: проверка, что файлов чужой
   раскладки нет и что в базе шарда нет ключей чужих цифр (`layout_check`, `strays`).
   Определения `server.bend` с бесконечными циклами помечены `@unsafe` и честно стоят вне
   гарантий.
3. **clang, libc, ОС.**
4. **Ресурсные пределы** — вне логики Bend. Переполнение `Nat` предотвращено конструктивно:
   целые ≤14 цифр, длины ≤10 цифр, топливо парсера — 2^32−1 (запрос не короче 4 байт).
   Но это аргумент, а не доказанный закон. Исчерпание кучи — аварийная остановка.

## Ограничения Bend2, выявленные на практике

- **Нет `match` по вычисленному значению и по let-переменной; рекурсия только структурная,
  без взаимной; функцию можно вызвать только выше по файлу.** Forward-declaration через
  `law` разрешена лишь Base. Приходится выносить ветвления во вспомогательные функции,
  а аргументы вычисляются строго — отсюда «жадные» вычисления (см. `bget`, `bdel`, `glob`)
  и топливо в парсере.
- **Аффинность.** Функция-гипотеза (`∀k. …` или опровержение `a != b`) используется один раз,
  а равенства — это `Data`, и их можно копировать. Поэтому опровержения переводятся в
  равенства булевых вердиктов (`{False == str_eq(j,k)}`). По той же причине
  доказательства уточнения относительно эталонной модели с ∀-инвариантом неудобны.
  Мы доказали законы напрямую. Закон о шардах поэтому сформулирован от старта сервера,
  для любой истории пачек: соответствие «под каждой цифрой корня шард держит то же
  поддерево, что и база» выводит заново функция верхнего уровня, а её можно вызывать
  сколько угодно.
- **`case other` в доказательстве не уточняет цель.** В функции `case other` покрывает
  оставшиеся конструкторы, а в доказательстве переменная остаётся абстрактной («`c`, но не
  `SizeAt`»), и функции от неё не редуцируются. Леммы о командах поэтому перечисляют все 20
  конструкторов, большую часть — опровержениями.
- **Чекер вычисляет `Nat` в унарной форме.** Константа вроде 10^14 переполняет стек
  чекера, поэтому проверка переполнения в INCR сделана по числу цифр.
- **Нет тактик и автоматизации.** Каждый шаг переписывания пишется руками, с явным мотивом.
  Доказательств получилось примерно столько же, сколько кода, — для ручного режима это
  неплохо. Проверка же действительно быстрая.
- **`match` идёт до локальных привязок, а разбор пары — только переменной.** `match x` после
  `%rewrite` или `+y = …` в том же теле не принимается; разбирать вложенную пару
  `(a, (b, c))` в одном теле чекер не умеет вывести — второй уровень уходит в отдельную
  функцию. Зато есть образцы `case 10n+m` и `case 1n++p` (дублируемая переменная), что
  и позволило делить на 10 «шагами по десять».
- **Представление данных:** в стоковом Bend строки — связные списки (патч упаковывает их
  в C-рантайме, см. PERFORMANCE.md), нет 64-битных чисел, мало эффектов (в стоке ввод-вывод
  файлов без `fsync`; двенадцатый патч добавляет его). Для СУБД это главный практический
  блокер.

## Как запустить

И доказательствам, и серверу нужен Bend с патчами: сервер использует
`TCP.recv_raw`/`TCP.send_raw` из второго патча, а карта хеширует ключи `String.hash`,
которое четвёртый патч добавляет в Base, подсказывает процессору `Mem.prefetch` из
девятого, циклы на нескольких ядрах, `Chan.send_all` и `TCP.post` берёт из десятого,
`TCP.post_list` — из одиннадцатого, а журнал — `File.write_raw`, `read_raw`, `sync` и
`truncate` из двенадцатого и `Chan.drain` из тринадцатого. На одном шарде соединение
отдаёт пачку актору и ждёт ответа одним `Chan.call`, а с писателем отвечает и ждёт
следующего запроса одним `TCP.post_recv_raw` (оба — из шестнадцатого). Разборщик читает
строки чисел и хеши ключей по индексу функциями из восемнадцатого. Четырнадцатый,
пятнадцатый, семнадцатый, девятнадцатый и двадцатый только ускоряют рантайм и код.
Makefile передаёт Bend `CC=clang-19`, если такой есть: clang 18 игнорирует соглашение
`preserve_none`, и код выходит на ~8% медленнее.

```bash
# Bend с патчами: клон bendlang/bend, на него двадцать патчей из bend-patches/;
# для --verdict нужен Lean 4.34.0 (elan)
git clone https://github.com/bendlang/bend ../../bend-patched
sh bend-patches/apply.sh ../../bend-patched
B="bun ../../bend-patched/bend2/main.ts"
make check BEND="$B"     # доказательства
make verdict BEND="$B"   # доказательства + перепроверка ядром BendTT (первый раз собирает ядро ~40 с)
make build BEND="$B"   # нативный сервер build/bendkv (clang, ~40 с)
make run               # ./build/bendkv 6380 (./build/bendkv 6380 2 — два шарда,
                       # ./build/bendkv 6380 2 post — два шарда с потоками-писателями,
                       # ./build/bendkv 6380 1 send — один шард без писателя,
                       # ./build/bendkv 6380 1 post data.aof always — с журналом,
                       # ./build/bendkv 6380 2 send data.aof — два шарда, data.aof.0 и .1)
redis-cli -p 6380 set foo bar
make test BEND="$B"    # устойчивость, дифференциальный тест против redis-server и
                       # согласованность при многих клиентах: 1 шард, 2 шарда, 2 с писателями,
                       # 1 и 2 с журналом; перезапуск из журналов и обрезанный хвост;
                       # отказы диска под журналом (нужен компилятор C)
make pgo BEND="$B"     # build/bendkv-pgo: сборка с профилем (нужен llvm-profdata)
make bench BEND="$B"   # redis-benchmark: BendKV против Redis
```

## Что дальше

1. **Журнал дальше.** Перезапись журнала (BGREWRITEAOF): снимок базы командами SET с
   законом, что он читается так же, как база (по ключам, а не по форме трая); он же
   позволит менять число шардов у файлов. Согласованный срез шардов после сбоя (сейчас
   каждый шард хранит префикс своих команд, а не все вместе — префикс команд сервера). Закон о
   продолжении: после обрезки и новых записей файл — журнал истории «префикс + новые
   пачки». И закон обратимости сетевого разбора `resp.bend`: формат журнала — те же
   массивы bulk-строк, что шлют клиенты, и он же доказал бы решение резать оборванный
   файл (`cut_short`).
2. **Новые типы данных:** списки, хеши, множества и ошибка WRONGTYPE с законами того же вида.
   Законы коммутативности придётся проверить заново: RENAME, SUNIONSTORE или LMOVE
   переносят значения между ключами.
   TTL — с явной моделью времени в состоянии.
3. **DBSIZE за O(1)** с доказанным инвариантом счётчика и закон полноты KEYS. Тот же
   инвариант («в бакете нет повторов ключа») пустит DBSIZE в законы о перестановке.
4. **Производительность и шарды.** Время запроса теперь в основном системное: меньше
   системных вызовов на запрос (`io_uring`, ожидание нескольких готовых сокетов); буферы
   постов без `malloc` (~690 инструкций на запрос без конвейера); продолжение после
   эффекта — без узла задачи; разбор RESP дешевле ещё раз (~1 370 инструкций на GET с
   хешем); шарды с байтами в ответах проверить на машине, где серверу достаётся больше
   трёх ядер. Чередование чистых задач в рантайме на вероятных промахах: выигрыш подсказок
   без ручной пакетизации. PGO в драйвере Bend (в BendKV — `make pgo`), аппаратный хеш
   (ключ уже хешируется один раз, раздел 7.22), INCR за один проход по траю. Предложить патчи в `bendlang/bend`
   (снять регрессию на бенчмарке `lexer`, цену страниц по 2 МиБ для коротких программ и
   уложиться в потолок размера `comp.ts`; первым — ленивое запечатывание: лучшее
   соотношение выигрыша и цены, и оно помещается в запас до потолка; затем девятнадцатый,
   перевод `IO` в продолжения). См. [PERFORMANCE.md](PERFORMANCE.md), разделы 7.14, 7.17, 7.23,
   7.24, 9.6 и 11.
5. **SQL-направление:** верифицированное B+-дерево в памяти, затем небольшой движок
   реляционной алгебры с законами корректности оптимизатора (по образцу
   `demos/proof_typed_eval`), и только потом — диск.
