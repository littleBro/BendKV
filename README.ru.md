# BendKV — формально верифицированное Redis-совместимое KV-хранилище на Bend2 (PoC)

Цель — оценить, можно ли переписать популярную open-source БД (SQLite, Redis и т. п.)
на [Bend2](https://github.com/bendlang/bend) так, чтобы получить формально
верифицированную БД или кэш, и проверить это на небольшом PoC.

Окружение: Bend 2.0.35 (`bendlang/bend` @ `1cce499`; старый `HigherOrderCO/Bend2`
теперь только указывает на новый репозиторий), Lean 4.34.0 для `--verdict`, clang 19,
эталон — Redis 7.0.15.

In English: [docs/FINDINGS.md](docs/FINDINGS.md) (what the work found),
[docs/DIRECTIONS.md](docs/DIRECTIONS.md) (verified databases, compilers, parallelism, and
where the work goes next), [tools/README.md](tools/README.md) (how it was measured).

## Короткий вывод

- **SQLite на Bend2 сейчас переписать нереалистично.** Мешает не только объём
  (~220 тыс. строк C), но и пробелы платформы: нет 64-битных целых и double, нет `fsync`,
  `rename`, блокировок и записи по смещению, файлы ограничены U32 (4 ГиБ), строки —
  связные списки. Даже лучшие верифицированные хранилища (IronKV, VeriBetrKV на Dafny,
  FSCQ и DaisyNFS на Coq) — это человеко-годы работы, и верифицированного SQL-движка
  уровня SQLite не существует.
- **Redis реалистичен как «верифицированное ядро + проверенная тестами оболочка»** — и PoC
  это подтверждает. Получилось ~3 320 строк кода ядра (с разбором команд, их времён и
  опций, сопоставлением с шаблонами Redis, несколькими базами, диапазонами и битами
  строк, 64-битными словами BITFIELD), ~950 строк сессий
  (состояние соединения и сервера), ~70 строк подсказок процессору, ~520 строк журнала
  (AOF), ~1 040 строк
  конфигурации (CONFIG по таблице Redis, плюс ~180 строк таблицы, которую пишет
  генератор), ~440 строк INFO, ~410 строк COMMAND (плюс ~300 строк таблицы команд от
  генератора) и ~6 960 строк доказательств, написанных руками, плюс ~1 700 строк
  16-ричных разборов трая, которые пишет генератор, и 64 закона (без комментариев и
  пустых строк). Bend проверяет их примерно за 5 с, а ядро BendTT (его корректность
  доказана в Lean) — за ~50 с.
  Доказано и восстановление после перезапуска: сервер с журналом (AOF в формате Redis)
  поднимает из файла ровно те базы, которые держал (их 16, как у Redis), а из файла,
  оборванного сбоем на любом байте, — базы после некоторого префикса своих действий. На ~266 тыс. случайных команд
  ответы байт в байт совпали с настоящим Redis 7; версии с траем на 16 детей прошли ещё
  ~1 050 тыс., из них текущая (с BITFIELD) — ~115 тыс. Шарды по ядрам и хеш ключа один раз были сделаны и
  доказаны, но окупались слабо и убраны ради простоты кода (раздел 14 PERFORMANCE.md):
  кода стало на 38% меньше, доказательств — на 38%.
- **Цена — скорость и память, и большую часть её удалось снять.** На исходном Bend при
  упоре в CPU (конвейер 16) BendKV был в 7–21 раз медленнее Redis, а памяти на ключ ему
  требовалось в ~5 раз больше. Причина — модель памяти рантайма Bend, а не верификация.
  Двадцать патчей к компилятору Bend ([`bend-patches/`](bend-patches/): ленивое
  запечатывание счётчиков, упакованные строки с байтовым вводом-выводом, заимствующее
  чтение, нативные строковые операции, перестройка узла на месте, страницы по 2 МиБ для
  кучи, выбор поля по цифре без таблицы переходов, строка из одного куска без узла,
  подсказка процессору о предвыборке, несколько ядер: циклы событий на своих потоках,
  отправка в несколько каналов одним шагом, отправка по TCP через поток-писатель;
  `epoll` вместо `select`; байтовый файловый ввод-вывод с `fsync` и приём из канала без
  ожидания — для журнала; `code_at` коротких строк в терме и отправки, которые цикл делит
  с писателем; отправки самим циклом, пока он успевает; чтение строки по индексу без
  среза; `IO`, скомпилированный в прямые продолжения; подсказка до байтов буфера;
  запись шире 32 слов — отдельный узел) и переделка горячих путей BendKV дали следующее:
  - по бенчмаркам самого Redis (его спецификации для `memtier_benchmark`, раздел 7.15
    PERFORMANCE.md) на миллионе ключей, сервер на одном ядре: загрузка со значениями по
    100 байт — 1,39 пропускной способности Redis, GET с конвейером 10 — 1,26, с
    конвейером 100 — 1,36, INCR — 1,00, GET без конвейера — 0,90;
  - на двух ядрах, когда ответы отправляет поток-писатель (раздел 7.16): загрузка —
    **1,94** от Redis, GET с конвейером 10 — **1,61**, с конвейером 100 — 1,39, INCR —
    1,27, GET без конвейера — 1,11. Redis с `io-threads 2` на тех же ядрах — 0,99–1,22 от
    себя однопоточного. Шарды по ядрам (были до раздела 14) на двух ядрах окупались
    только без конвейера (1,19), а с конвейером один цикл с писателем быстрее, потому что
    термы, переходящие между ядрами, дороже параллельной работы с картой;
  - с `epoll` вместо `select` (одиннадцатый патч, раздел 7.17) GET без конвейера на тех
    же двух ядрах — **1,27** от Redis (с `select` в той же серии — 1,15), время ядра ОС
    на запрос на 30% меньше. На трёх ядрах сервера один цикл с писателем даёт 897 тыс.
    GET/с с конвейером 10 — 2,06 от Redis с тремя io-threads (три шарда тогда давали
    816 тыс.). Сборка с профилем (`make pgo`) добавляет 1–4%;
  - при конвейере 16 на заполненной базе из 100 тыс. ключей (`redis-benchmark` со
    значениями по 3 байта: лучший для BendKV случай) BendKV быстрее Redis:
    **GET 1,62** его пропускной способности, **SET 1,82**, **INCR 1,45** (было 0,08–0,14).
    На миллионе ключей — 1,65, 1,80 и 1,17. Так стало с подсказками процессору по пачке:
    до них было 1,17–1,21, 1,10–1,15 и 0,95–0,96 на 100 тыс. ключей и 1,02–1,14,
    1,06–1,24 и 1,04–1,12 на миллионе (по сериям двух дней на разных ВМ). На тысяче
    ключей, где всё и так в кэше, — 1,09, 1,13 и 0,95;
  - без подсказок инструкций на запрос меньше, чем у Redis: на GET 3 280 против 3 549,
    на SET 3 985 против 4 773, на PING 2 172 против 2 438; на INCR — 4 209 против 3 948.
    Промахов мимо L2 на GET и SET тоже меньше: 2,4 и 2,8 против 2,7 и 3,3. Подсказки
    добавляют 14–17% инструкций (GET 3 834), зато прячут ~85% ожидания памяти;
  - без конвейера BendKV держит 118–132% пропускной способности Redis;
  - памяти на ключ нужно вдвое меньше, чем Redis: ~63 байта против ~128 на ~950 тыс.
    ключей (60 МБ RSS против 121 МБ) при значениях по 3 байта; при 100 байтах — 192
    байта против 221 (0,87 от Redis), и чтение её не прибавляет (до раздела 7.25
    PERFORMANCE.md первый GET значения добавлял ему 8 байт);
  - SET значения 1 МБ — 4,4 мс, GET — 1,4 мс (у Redis ~1 мс);
  - с журналом (AOF, раздел 7.19) при `everysec`, умолчании обоих, BendKV с конвейером 16
    быстрее Redis с тем же журналом: SET в **1,96** раза, INCR в 1,76, GET в 1,74; при
    `always` — в 1,15–1,73. Без конвейера при `always` они равны: оба упираются в
    `fdatasync` и оба объединяют запросы клиентов в одну синхронизацию. Журнал из
    миллиона SET BendKV читает за 1,62 с, Redis — за 1,24 с;
  - по спецификациям Redis на двух ядрах сервера, у всех журнал с `everysec`: BendKV —
    1,17–1,87 от Redis (раздел 7.21; два шарда с журналами давали 1,02–1,71, без конвейера
    они были быстрее одного цикла в 1,3–1,5 раза). Журнал из миллиона SET BendKV
    восстанавливает за 1,05 с, Redis — за 1,38 с в той же серии;
  - после пяти шагов по разбивке профиля (раздел 7.23 PERFORMANCE.md: разбор RESP
    дешевле, длинные чтения окнами, цикл делит отправки с писателем, эффекты парами;
    подсказки на всю группу актора сделаны, измерены и убраны) инструкций на запрос на
    8–9% меньше при конвейере 16, на 19% без конвейера и на 44–54% при конвейере 100. По
    спецификациям Redis на двух ядрах: загрузка — **1,93** от Redis, GET с конвейером 10 —
    1,46, без конвейера — **1,37**, с конвейером 100 — **1,69**, INCR — 1,43 (в той же
    серии до шагов: 1,73, 1,43, 1,23, 1,35 и 1,39). Без конвейера под `redis-benchmark`
    (один поток клиента) Redis был быстрее: BendKV с писателем — ~0,80 от него;
  - после ещё трёх шагов (раздел 7.24 PERFORMANCE.md) этот разрыв закрыт: цикл
    отправляет ответы сам, пока успевает за сокетами, и без конвейера под
    `redis-benchmark` BendKV — 0,93–1,05 от Redis на GET и 0,90–0,98 на SET (три серии).
    Запрос разбирается сразу в команду вместе с хешем ключа и доказательством, что хеш
    подходит, а `IO` компилируется в прямые продолжения: вместе это ещё 10–14% инструкций
    (GET 2 969, SET 3 534, INCR 3 830 при конвейере 16), но по времени меньше шума — ядро
    теперь около половины CPU запроса. По спецификациям Redis на двух ядрах: загрузка —
    **2,25** от Redis, GET с конвейером 10 — 1,62, без конвейера — 1,37, с конвейером
    100 — **1,95**, INCR — 1,39; при конвейере 16 на одном ядре — **1,86, 1,83 и 1,54**
    на GET, SET и INCR.

  Куда смотреть, показывал профиль по времени, снятый сэмплированием по таймеру
  ([`tools/sprof.c`](tools/sprof.c)). Строки до 6 байт лежат прямо в слове терма, и
  значение `"xxx"` не стоит ни одного промаха; строка из одного куска — сам буфер, и
  сравнение ключа стоит один промах, как у Redis. Перед каждой пачкой BendKV проходит пути
  всех её ключей уровень за уровнем, только начиная загружать следующий уровень
  (`Mem.prefetch`), и промахи разных ключей перекрываются; закон `batch_hints` доказывает,
  что это ничего не меняет. На одном ядре медленнее Redis BendKV там, где пачек нет: GET
  без конвейера (0,90, путь одной команды через соединение, канал и актор дороже, чем у
  Redis) и INCR на маленькой базе (0,95 на тысяче ключей). Подробный разбор и план — в
  [PERFORMANCE.md](docs/PERFORMANCE.md).
- **Что значит «верифицирован».** Доказано, что *исходный код* на Bend удовлетворяет
  законам. Компилятор Bend (по README проекта — на 99% написан ИИ и не прошёл аудит),
  его C-рантайм, clang и ОС остаются в доверенной базе. Это не end-to-end-верификация
  в духе CompCert/seL4.
- Bend2 **больше не использует HVM** — у него собственный рантайм BendRT
  (C/CUDA/Metal/JS).

## Оценка кандидатов

| Кандидат | Объём оригинала | Что нужно от платформы | Блокеры в Bend2 сегодня | Вердикт |
|---|---|---|---|---|
| **SQLite** | ~220 тыс. строк C/H в `src/` (B-дерево 11,7 тыс., pager 7,9 тыс., WAL 4,8 тыс., VDBE 9,6 тыс.) | 64-битные INTEGER и REAL, файлы > 4 ГиБ, запись страниц по смещению, `fsync`, блокировки, разбор SQL (взаимная рекурсия) | Нет I64/F64 (F32 аксиоматичен — о нём ничего нельзя доказать). Файлы: только open/read/read_at/size/write/close, смещения U32, без `fsync`/`rename`/lock. Нет взаимной рекурсии. Строки — списки | **Нет.** Разумный шаг: верифицированное ядро таблиц (B+-дерево в памяти + реляционная алгебра) |
| **Redis** | ~212 тыс. строк C/H, 240 команд в 7.0.15 (строковые, `t_string.c`, — ~1,7 тыс. строк) | Хеш-таблица, бинарно-безопасные строки, int64, RESP, событийный цикл, AOF/RDB, TTL | int64 → пришлось ограничить целые 14 цифрами. Персистентности в стоке мешает отсутствие `fsync` (патч 12 его добавляет; AOF с доказанным восстановлением сделан). TTL требует модели времени | **Да, по частям.** Семантика команд — чистая функция `(команда, состояние) → (ответ, состояние)`, идеальна для доказательств. PoC сделан |
| **memcached-подобный кэш** | Меньше Redis | GET/SET/DELETE/INCR, LRU-вытеснение | Те же, что у Redis, плюс доказательства политики вытеснения | **Да.** Ещё проще Redis |
| **LMDB/LevelDB-подобное встраиваемое KV на диске** | ~10–30 тыс. строк | B+-дерево/LSM на диске, атомарные коммиты, восстановление после сбоя | Нет `fsync`/`rename`/записи по смещению. Нужна модель сбоев (как Crash Hoare Logic в FSCQ) | **Не сейчас.** Нужны собственные эффекты на C и своя модель диска |

## Что сделано: BendKV

Redis-совместимый сервер (RESP2) в памяти. Работают `redis-cli` и `redis-benchmark`.

```
src/server.bend  TCP, соединения, актор базы, файл журнала, лог ─┐ не верифицирован (@unsafe-циклы),
src/startup.bend командная строка и файл конфигурации            │ проверен тестами
src/info.bend    INFO: секции и поля Redis                       │
src/command.bend COMMAND: таблица команд BendKV из Redis           │
src/resp.bend    разбор RESP2 и сериализация ответов            ─┘
src/session.bend соединение и сервер: состояние, пачка целиком  ─┐ верифицирован:
src/config.bend  параметры, CONFIG GET и SET                     │
src/aof.bend     журнал: эффекты пачки, запись, чтение, повтор   │ proof/LAWS.bend
src/batch.bend   пачка с подсказками процессору                  │ + proof/PROOF.bend
                                                                 │ (+ proof/SPEC.bend)
src/redis.bend   семантика команд: exec(cmd, db) → (reply, db')  │
src/map.bend     хеш-трай со строковыми ключами                 ─┘
```

**Команды:** PING, ECHO, GET, SET, SETNX, GETSET, DEL/UNLINK, EXISTS, INCR, DECR, INCRBY,
DECRBY, APPEND, STRLEN, MGET, MSET, MSETNX, RENAME, RENAMENX (время ключа переходит
вместе с ним), COPY (DB и REPLACE; время ключа копируется вместе с ним), DBSIZE, KEYS (шаблоны
Redis: `*`, `?`, классы `[...]`, экранирование `\`), TYPE, TOUCH, SCAN (MATCH, COUNT, TYPE;
с гарантией Redis: ключ, который был в базе весь обход, обход найдёт, как бы база ни
менялась в это время) и RANDOMKEY (ключ выбирается так же, как его выбирает Redis).
OBJECT (ENCODING, REFCOUNT, IDLETIME, FREQ, HELP) отвечает по значению: кодировок и
времени доступа BendKV не хранит. ENCODING — как Redis кодирует значение, заданное
целиком (а значение, сделанное APPEND, SETRANGE или SETBIT, у Redis `raw`), REFCOUNT — по
общим целым Redis при текущей политике вытеснения, IDLETIME и FREQ — 0 (с отказом при
той политике, при которой отказывает Redis). TIME — время, в которое идёт пачка, с
точностью до миллисекунды.
Диапазоны и биты: GETRANGE (и SUBSTR), SETRANGE, GETBIT, SETBIT, BITCOUNT и BITPOS (с
диапазонами в байтах и битах, BYTE и BIT): числа читаются, как их читает Redis, ошибки —
там же, где у Redis; значение растёт не больше чем до 512 МБ (proto-max-bulk-len по
умолчанию). SETRANGE и SETBIT пишут в журнал SETRANGE записанных байтов, а не всё
значение. BITOP (AND, OR, XOR, NOT; в журнал — SET его значения) и LCS (LEN, IDX,
MINMATCHLEN, WITHMATCHLEN; таблица ограничена proto-max-bulk-len, как в Redis, и считается
медленно — примерно в двадцать раз дольше, чем у Redis). BITFIELD и BITFIELD_RO: поля до 64
бит, со знаком и без, по смещению в битах или `#k`, с GET, SET, INCRBY и OVERFLOW WRAP,
SAT и FAIL, в 64-битной арифметике C, как у Redis; в журнал — SETRANGE байтов, до которых
дошли его записи. Поле поперёк 2^32-го бита, ради которого Redis растит значение больше
512 МБ, отвергается ошибкой SETRANGE.
Хеши: HSET, HMSET, HSETNX, HGET, HMGET, HDEL, HLEN, HSTRLEN, HEXISTS, HKEYS, HVALS,
HGETALL, HINCRBY, HSCAN (MATCH, COUNT) и HRANDFIELD (со счётчиком, с повторами при
отрицательном, WITHVALUES; выбор — по случайным числам сервера); аргументы и ошибки — как
у Redis. Пока хеш мал (не больше 512 полей, поля и значения не длиннее 64 байт — пределы
listpack в Redis по умолчанию), BendKV хранит поля в порядке прихода, а дальше — в своём
трае, уже навсегда, как Redis переводит listpack в hashtable: малый хеш HSCAN отдаёт
целиком с курсором 0, большой — по корзинам. OBJECT ENCODING отвечает `listpack` или
`hashtable`, как ответил бы Redis при текущих параметрах; команды строк отвечают на хеш
WRONGTYPE, команды хешей — на строку. MEMORY USAGE (SAMPLES) оценивает размер ключа в
байтах. В журнал запись хеша идёт как HSET установленных пар или HDEL снятых полей
(HINCRBY — как HSET его суммы); хеш, сделанный там, где ещё лежал истёкший ключ, — одной
записью EVAL с постоянным скриптом, который удаляет ключ и ставит пары: Redis исполняет
его при загрузке, BendKV разбирает обратно (сам Redis пишет MULTI с DEL и HSET — две
записи, между которыми может оборваться файл). Другого Lua BendKV не исполняет, кроме
таких же скриптов списков (ниже).
Списки: LPUSH, RPUSH, LPUSHX, RPUSHX, LPOP и RPOP (со счётчиком), LLEN, LINDEX, LRANGE,
LSET, LINSERT, LREM, LTRIM, LPOS (RANK, COUNT, MAXLEN — как их читает Redis 7.0.15,
включая RANK, равный LLONG_MIN), LMOVE, RPOPLPUSH и LMPOP; аргументы и ошибки — где и как
у Redis (счётчик и индекс могут быть любым long long). Список — дек из двух стеков, так
что добавление и снятие с любого конца стоит O(1) в среднем, а LINDEX и LRANGE идут от
ближнего конца; пустого списка ключ не держит. OBJECT ENCODING отвечает `quicklist`, как
Redis 7.0 для любого списка, MEMORY USAGE оценивает его размер. В журнал запись списка
идёт как сама запись (LMPOP — как LPOP или RPOP ключа, с которого он снял, со счётчиком;
снятие последних элементов — как DEL ключа); список, сделанный там, где ещё лежал
истёкший ключ, — записью EVAL того же скрипта, что у хешей, с добавлениями, а перенос
на такой ключ — одной записью EVAL постоянного скрипта, который удаляет приёмник и
выполняет LMOVE: Redis исполняет их при загрузке, BendKV разбирает обратно.
Блокирующих команд (BLPOP, BRPOP, BLMOVE, BLMPOP, BRPOPLPUSH) пока нет.
Сроки жизни: EXPIRE, PEXPIRE, EXPIREAT и PEXPIREAT (с NX, XX, GT, LT), TTL, PTTL,
EXPIRETIME, PEXPIRETIME, PERSIST; SET с NX, XX, GET, EX, PX, EXAT, PXAT и KEEPTTL; SETEX,
PSETEX, GETEX (EX, PX, EXAT, PXAT, PERSIST) и GETDEL. Времена читаются, как их читает
Redis, с его ошибками, и ключ истекает в своё время для каждой команды. Истёкший ключ
удаляет запись, которая к нему придёт, или чистка истёкших ключей десять раз в секунду
(в журнал она пишет DEL, как Redis); до тех пор его считают DBSIZE и строка keyspace в
INFO, а Redis удаляет его и тогда, когда к нему приходит чтение. Время от 10^14 мс (5138
год) и позже не даёт ключу срока вовсе.
Базы: их 16 или столько, сколько скажет `databases`, как в Redis: SELECT, MOVE (ключ
вместе со сроком), SWAPDB, FLUSHDB и FLUSHALL (с ASYNC/SYNC, которые опустошают сразу), с
ошибками Redis для неверного номера; в строке keyspace INFO — строка на каждую базу с
ключами, а чистка истёкших ключей обходит все базы.
Соединение: HELLO (RESP2; с
AUTH и SETNAME), AUTH (пароль или `default` и пароль), SELECT, QUIT, RESET (снова
выбирает базу 0), CLIENT ID, GETNAME, SETNAME, REPLY ON/OFF/SKIP, NO-EVICT,
GETREDIR, TRACKINGINFO, CACHING, UNBLOCK, HELP (слежения за ключами и блокирующих команд
нет, и эти подкоманды отвечают, как Redis, когда они не включены), FUNCTION FLUSH (функций
нет, сбрасывать нечего).
Конфигурация: CONFIG GET (имена, вторые имена, glob-шаблоны), SET (несколько параметров
сразу — все или ни одного), RESETSTAT, REWRITE, HELP по всем 178 параметрам Redis 7.0.15:
таблицу пишет `tools/gen_config.py` из `config.c` самого Redis, каждое значение
проверяется, как его проверяет Redis, и читается обратно, как его печатает Redis.
Действуют `requirepass` (пароль) и `hz` (с ограничением, как в Redis); порт, адреса, TLS
и журнал во время работы не меняются (новое значение отвергается той же ошибкой, что у
Redis, когда он не может его применить); остальные параметры хранятся и читаются, но
ничего не настраивают: вытеснения, репликации и кодировок в BendKV нет.
INFO — секции и поля Redis 7.0.15 в его порядке; секции выбираются, как у Redis (без
аргументов, `default`, `all`, `everything`, имена в любом регистре): server, clients,
memory, persistence, stats, replication, cpu, modules, errorstats, cluster, keyspace.
Значения свои там, где они у BendKV есть: процесс, параметры, соединения, команды и байты
(мгновенные скорости — выборки каждые 100 мс, как в `serverCron` Redis), резидентная
память, ключи, журнал; для того, чего у BendKV нет (репликация, `fork`, скрипты,
вытеснение), — то, что показывает Redis, когда этого нет. CONFIG
RESETSTAT начинает счёт заново. Статистика по командам считается так же, как у Redis:
вызовы каждой команды и подкоманды, вызовы, отклонённые до выполнения (неверное число
аргументов по арности Redis, клиент без пароля), и упавшие при выполнении; ответы-ошибки
по коду (errorstats), в том числе те, что клиент не получил (CLIENT REPLY OFF). Время
команд BendKV не замеряет: usec — 0, latencystats пуст.
COMMAND (с INFO, DOCS, COUNT, LIST и его фильтрами, GETKEYS, GETKEYSANDFLAGS, HELP)
описывает каждую команду BendKV и каждую её подкоманду, которая есть в BendKV, так, как
их описывает Redis 7.0.15: описания `tools/gen_commands.py` берёт у самого Redis.
Запуск — как у `redis-server`: файл конфигурации, параметры `--имя значение` и `-` для
стандартного ввода читаются по строке так же, как их читает Redis (`include`; `dir`,
который сразу меняет каталог; точки `save`, которые складываются; те же ошибки на тех же
строках), а лог пишется в форме Redis — в стандартный вывод или в `logfile`. Действуют
порт, `bind` (IPv4), `requirepass`, `protected-mode`, журнал (`appendonly`,
`appendfilename`, `appendfsync`, `aof-load-truncated`), `logfile`, `loglevel` и
`pidfile`; чего BendKV не умеет (модули, пользователи ACL, переименование команд, работа
в фоне, кластер, реплика, TLS, сигнал супервизору, файл RDB или многочастный журнал
Redis 7), то останавливает запуск строкой в логе.
Поддержаны конвейеризация, частичные пакеты, inline-команды (можно работать через `nc`)
и бинарно-безопасные значения.

**Устройство.** Команды исполняет актор баз данных. Как и в Redis, все команды
выполняются последовательно, в порядке поступления. Базы актор держит застёжкой
(zipper, `R.Ds`): одна в фокусе, остальные по обе стороны от неё; перед пачкой
соединения он переводит фокус на базу, которую соединение выбрало, и команды одной базы
исполняются на фокусе так же, как на единственной базе. Соединения разбирают запросы
и отправляют их актору пачками через каналы. Актор забирает разом все пачки, которые его
ждут (`Chan.drain`), исполняет их по очереди и отвечает всем одним шагом
(`Chan.send_all`). Ответы отдаются потоку-писателю (`TCP.post`), и цикл не ждёт
системного вызова `send`; писатель включается сам, когда процессу доступны хотя бы два
ядра (на одном он только отнимал бы время у цикла); `io-threads 1` отправляет из цикла,
как Redis с одним потоком, а короткая форма `./bendkv PORT post` или `send` выбирает
явно. Раньше базу можно было разделить на шарды по ядрам, но они окупались
только без конвейера и с журналом, а стоили двух файлов кода и двух пятых доказательств; в
разделе 14 docs/PERFORMANCE.md они убраны (код — в ветке
[`archive/shards`](https://github.com/littleBro/BendKV/tree/archive/shards)).

**Сессии.** Состояние соединения (`session.bend`: id, аутентифицирован ли клиент, имя,
режим CLIENT REPLY, просил ли он закрыться) едет к актору вместе с пачкой и возвращается
с ответами; состояние сервера (пока пароль) актор держит рядом с базой. Команды
соединения и сервера разборщик собирает в одну команду `Own`, а чтения одного ключа,
ответ которых зависит только от его значения (TYPE), — в `Peek`: законы видят каждую
группу одной командой, и новая команда в группе не прибавляет доказательств. Пачку из
одних команд базы от клиента, который их может исполнять и получает все ответы,
актор исполняет как прежде (`exec_batch`, `log_batch`); любую другую — по команде за
раз (`S.gen`): команда после QUIT отбрасывается, ошибка разборщика отвечается, команда
клиента, который должен сначала войти, отвергается (NOAUTH), команда сессии исполняется
с состоянием, команда базы — через `exec`, а ответ уходит или нет, как велит CLIENT
REPLY. Соединение после ответов идёт дальше без замыканий-продолжений: шаги `@unsafe`
вызывают друг друга и цикл соединения напрямую. Сессии стоят от −0,5 до +0,2%
инструкций на запрос при конвейере 16 и +2% без конвейера (раздел 15 PERFORMANCE.md).

**Журнал (AOF).** С `appendonly yes` (или `./bendkv PORT post|send FILE [always|everysec|no]`) актор исполняет
пачку через `exec_log` (`aof.bend`, после подсказок процессору, как обычно): кроме ответов и базы она даёт эффекты — что пачка
сделала, в виде команд. Чтение не даёт ничего, SET, SETNX, GETSET, APPEND, DEL, MSET и
FLUSHDB — себя, а INCRBY — SET нового значения (так Redis пишет INCRBYFLOAT): при чтении
журнала из текста разбираются только сроки и номера баз. Эффект привязан к своей базе:
перед записями другой базы, чем та, что файл выбрал последней, идёт SELECT, а SWAPDB,
MOVE и FLUSHALL пишутся, как их пишет Redis (MOVE — после SELECT базы, из которой ключ
уходит), а COPY — после SELECT базы, из которой ключ копируется, всегда с DB и REPLACE:
при повторе в момент 0 целевой ключ с прошедшим временем был бы «есть». COPY, как его
пишет Redis (как прислал клиент: без DB — в выбранную базу, опции в любом порядке и
регистре), журнал при загрузке тоже читает. Эффекты дописываются в файл до ответа
клиенту, в формате AOF самого Redis (массивы bulk-строк). Актор берёт запрос и вместе с
ним все, что пришли, пока он работал (`Chan.drain`), исполняет их пачки одну за другой,
пишет их эффекты одной записью, при `always` делает один `fsync` и отвечает всем сразу
(групповая фиксация, как в цикле Redis). При `everysec` (умолчание, как у Redis) файл
синхронизирует раз в секунду отдельное вычисление через свой дескриптор, при `no` — ОС.
При старте сервер читает файл и исполняет его записи на пустых базах (SELECT переводит
фокус). Если файл кончается
посреди записи (сбой во время `write`), он обрезается до последней целой записи, как в
Redis с `aof-load-truncated yes`, и доказано, что базы тогда — те, что были после
некоторого префикса действий; что-то иное после записей — отказ стартовать, тоже как
в Redis. Файл, который есть, но не открывается (нет прав, ошибка ввода-вывода, нет
свободных дескрипторов), — тоже отказ: пустая база с дописыванием в старый файл
разошлась бы с ним. Неудавшийся `fsync` останавливает сервер и при `everysec`, как при
`always`: подтверждённые записи могли не попасть на диск, а ядро после такой ошибки
может выбросить грязные страницы, и следующий удачный `fsync` этого не покажет (Redis
в этом случае отвечает на записи ошибкой `MISCONF`, пока `fsync` снова не пройдёт).

**Хранилище** — трай на 16 детей по 5 шестнадцатеричным цифрам хеша FNV-1a (2^20 бакетов).
Бакет — цепочка записей прямо в трае, на случай коллизий; запись хранит ключ, значение и
время, когда ключ истекает (в мс от 1970 года; 0 — никогда). Структура выбрана ради
доказуемости: не нужен порядок на ключах (как в деревьях поиска), а разные пути ведут в
разные узлы. Поэтому законы доказываются индукцией по глубине обхода. Для корректности хеш
может быть любым; хороший хеш лишь сокращает бакеты. Обходы идут по цифрам самого хеша,
каждая цифра вычисляется заранее и передаётся параметром. Чтение ключа (`get`) ищет в
бакете прямо в конце обхода и только одалживает базу: компилятор с патчем `borrow-reads`
удерживает найденное значение на месте, а не разделяет весь трай. GET сервера отвечает
копией значения, сделанной там же (`get_copy`): значение в базе остаётся
неразделённым, без ячейки-счётчика, и подсказки по пачке доходят до его байтов; доказано,
что копия и есть значение (`tget_kc_eq`). Запись перестраивает путь на месте. 16- и 256-кратные разборы в коде и в доказательствах пишет
`tools/gen_trie.py`.

### Что доказано (proof/LAWS.bend)

Законы формулирует человек, доказательства (`PROOF.bend`) пишет и проверяет машина.

**Отображение (11 законов).** Это полная аксиоматизация конечного отображения ключей на
запись — значение и время: после любой последовательности записей четырёх видов
(значение со временем, значение с прежним временем, одно время, удаление) запись любого
ключа однозначно определена, значит, устаревших, потерянных или «чужих» записей не
бывает.
- `entry_empty` — в пустой базе нет ключей;
- `entry_setx_same`, `entry_setx_other` — после записи значения со временем ключ хранит
  их, а остальные ключи — то, что хранили;
- `entry_keep_same`, `entry_keep_other` — значение с прежним временем (KEEPTTL, INCR,
  APPEND): ключ хранит новое значение и время, которое у него было (новый ключ — без
  времени);
- `entry_expire_same`, `entry_expire_other` — одно время (EXPIRE, PERSIST): ключ хранит
  своё значение с новым временем, а ключа, которого нет, такая запись не создаёт;
- `entry_del_same`, `entry_del_other` — после удаления ключа нет, остальные — как были;
- `get_entry`, `read_entry` — чтение отдаёт значение записи; `read`, которым читают
  команды, — только пока время ключа не прошло.

**Ключи (2 закона).** `key_eq_true` и `key_eq_false`: сравнение ключей `str_eq` — это ровно
равенство строк. `str_eq` — это `String.eq` из Base (в C-рантайме с патчем — `memcmp` по
кускам); доказано, что оно совпадает с посимвольным сравнением, а доказательство спускается
по представлению до 32 битов `U32`.

**Команды (24 закона)** о функции `exec`, которую сервер и исполняет:
- `frame` — **ни одна команда не меняет ключ, который она не пишет, — ни его значение, ни
  его время**: SET/DEL/MSET/INCR/EXPIRE/… трогают только названные ключи, FLUSHALL — все.
  Доказано для всех 17 видов команд (с группами `Peek`, `Upd` и `Own`);
- `reads_keep_db` — команды чтения (GET, EXISTS, MGET, STRLEN, KEYS, SCAN, DBSIZE, PING,
  ECHO, ошибки) не меняют базу целиком;
- `get_after_set`, `get_missing` — GET после SET и GET ключа, которого нет (не ставили,
  удалили или истёк);
- `expired` — **ключ, время которого прошло, не существует ни для одной команды**: GET
  отвечает nil, DEL его не считает, SETNX ставит заново;
- `del_effect` — после DEL удалён каждый названный ключ (с повторами и в любом порядке);
  `del_one_count` — DEL одного ключа отвечает 1 или 0;
- `append_effect` — APPEND ключа без коллекции сохраняет «старое ++ новое» и отвечает
  новой длиной; новый ключ прибавляется к счётчику ключей базы;
- `setrange_effect` — SETRANGE существующего ключа со строкой пишет байты со смещения (дополняя
  значение нулевыми байтами), сохраняет ключу время и отвечает новой длиной, когда он
  ключ меняет (непустые байты, значение не больше 512 МБ); изменение SETBIT — такой же
  SETRANGE своего байта;
- `setnx_missing` и `setnx_present` — SETNX ставит отсутствующий ключ (счётчик растёт на
  один) и не трогает существующий;
- `incr_missing` — INCR отсутствующего ключа сохраняет "1" без времени, отвечает 1 и
  считает ключ;
- `pttl_left` — PTTL ключа со временем отвечает, сколько миллисекунд ему осталось;
- `set_keepttl` — SET с KEEPTTL сохраняет ключу его время, какого бы типа ни было
  значение;
- `persist_effect` — PERSIST снимает время с ключа и отвечает 1;
- `getdel_effect` — GETDEL ключа со строкой отвечает ею и удаляет ключ;
- `rename_effect` — RENAME ключа, который есть, в другой ключ переносит запись (значение и
  время) и отвечает OK: исходного ключа нет, а целевой держит то, что держал исходный,
  что бы в нём ни было раньше;
- `msetnx_present` и `msetnx_missing` — MSETNX ничего не ставит и отвечает 0, если хоть
  один его ключ есть, а иначе ставит все, как MSET, и отвечает 1;
- `bitop_store` — после BITOP целевой ключ держит значение, которое дали источники, без
  срока (или удалён, если значение пустое), а ответ — длина значения, если ни один
  источник не держит коллекцию (иначе WRONGTYPE);
- `reap_keeps` — **чистка истёкших ключей не удаляет ни одного ключа, который есть**:
  она удаляет через DEL ключи, которые оставил фильтр `reap.keys` из найденных обходом,
  что бы обход ни нашёл;
- `batch_step` и `batch_nil` — **пакет команд исполняется ровно как последовательность
  команд**. Это связывает законы об одной команде с тем, как сервер исполняет
  конвейеризированные пачки;
- `batch_hints` — **подсказки процессору ничего не меняют**: сервер исполняет пачку через
  `batch.bend`, который сначала начинает загружать в кэш пути её ключей (по хешам, которые
  разборщик прочёл из запросов), а потом исполняет её как `exec_all`; закон верен при любых
  хешах.

База — запись `Db`: трай, число ключей в нём (его отдают DBSIZE и строка keyspace в INFO),
число ключей со временем и время, в которое идёт пачка; баз несколько, и пачка идёт на
той, что в фокусе. Законы о том, как читаются ключи
и что отвечают команды, доказаны о спецификации — `exec` на одном трае в момент времени
(`proof/SPEC.bend`); мост
(`bridge_go`) доказывает, что `exec` сервера отвечает, как спецификация, и оставляет тот
же трай (кроме ответа DBSIZE — это счётчик). Законы о базе целиком доказаны на записи
вместе со счётчиком. Что счётчик равен размеру трая, пока не доказано.

**Коммутативность (5 законов).** Команды на разных ключах можно исполнять в любом
порядке. Ключ после команды зависит только от того, как до неё читались он сам и ключи,
от которых зависят записи команды (`deps`): RENAME переносит значение с одного ключа на
другой, MSETNX ставит свои ключи, только если ни одного из них нет, BITOP ставит целевой
ключ по своим источникам. Поэтому:
- `commute_reads` — после двух команд в любом порядке каждый ключ, который пишет не
  больше одной из них, читается одинаково, если ни одна не пишет ключ, от которого
  зависят записи другой (`spoils`);
- `commute_reply` — команда отвечает так же после другой, которая её не «тревожит»
  (`disturbs`: не пишет ни один ключ, который первая читает; для DBSIZE, KEYS и SCAN —
  вообще ничего не пишет);
- `commute` — две команды, не тревожащие друг друга, дают те же ответы в любом порядке;
- `swap_replies` и `swap_reads` — **две соседние независимые команды пачки можно
  поменять местами** (независимые — не пишут общих ключей и ни одна не пишет ключ, от
  которого зависят записи другой): их ответы меняются местами, остальная пачка отвечает так же
  (если в ней нет DBSIZE, KEYS и SCAN), а в конце каждый ключ читается одинаково (это —
  при любой остальной пачке).

Законы говорят о том, как читаются ключи, а не о самом трае: два новых ключа одного
бакета лежат в порядке записи, и KEYS и SCAN могут перечислить их в другом порядке
(Redis порядка и не обещает). Поэтому DBSIZE, KEYS и SCAN после перестановки исключены:
для них понадобился бы инвариант «в бакете нет повторов ключа».

**Персистентность (8 законов)** о журнале (`aof.bend`):
- `log_exec` — `exec_log` отвечает и меняет базу ровно как `exec_all`: с журналом сервер
  отвечает так же, как без него;
- `log_hints` — подсказки процессору и здесь ничего не меняют: актор исполняет пачку
  через `log_batch`, и при любых хешах это ровно `exec_log`;
- `log_replay` — эффекты пачки, исполненные в момент 0 на той базе, на которой
  исполнялась пачка, дают ту же базу, что и пачка (в момент 0: файл загружается в момент
  0, когда ни один ключ не истёк, а эффекты называют каждое время от 1970 года);
- `log_args` — эффекты любой пачки, записанные строками запроса, разбираются обратно в
  себя; время в них — такое, какое ключ хранит (меньше 10^14 мс), и разбор времён
  (`num14`) читает обратно то, что записал `Nat.show` (`num14_show`);
- `aof_load` — **файл читается ровно как записанные в него записи**, и ничего не остаётся.
  Здесь доказан и десятичный круговой путь: длину, записанную `Nat.show`, разбор цифр
  читает обратно (через деление на 10 «шагами по десять» и топливо `Nat.show`);
- `recover` — **после любой истории пачек, каждая в своё время и на любой из баз,
  сервер восстанавливает из своего файла ровно те базы, которые держал** (в момент 0:
  время сервер ставит перед следующей пачкой), и после последней записи ничего не
  остаётся. Воспроизведение файла держит инвариант с базами сервера: каждая база в
  момент 0 читается так же, фокус воспроизведения — база, которую файл выбрал последней,
  а его время — 0; действие без эффекта (переведённый фокус, SWAPDB или MOVE, который
  ничего не сделал, команда, которая ничего не записала) оставляет базы такими же в
  момент 0, а действие с эффектом делает с воспроизведением то же, что с базами сервера.
  Номера баз в файле короче 15 цифр, и разбор читает обратно то, что записал `Nat.show`;
- `recover_cut` — **файл, оборванный сбоем на любом байте, восстанавливает базы, которые
  сервер держал после некоторого префикса своих действий**: ни одно действие не
  применено частично, ни одно — не по порядку и ни одно — после потерянного. Оборванная
  запись никогда не читается (строка числа без `\r\n`, bulk без байтов или без `\r\n`);
  эффект — одна запись или SELECT и одна запись, а SELECT без записи за ним не меняет
  ни одной базы; у действия не больше одного эффекта: первые k записей дают базы после
  первых j действий, для некоторого j;
- `load_cut` — прочитанные целые записи, записанные снова, вместе с остатком и есть
  оборванный файл: сервер отрезает ровно остаток, и в файле остаются целые записи.

Мутации журнала (не писать APPEND, писать в INCR не то число, сдвинуть цифру, отнять у
загрузчика топливо, записать лишний элемент в счётчик массива, потерять пару MSET, не
отрезать тело bulk-строки) ломают доказательство ровно в том месте, которое они портят.
Ещё две мутации загрузчика проходят все законы о целом файле, и их ловят только законы
об обрыве: bulk, оборванный посреди байтов, читается как строка короче (значение,
которого никто не писал), а запись, оборванная между аргументами, — из того, что успело
дойти (DEL a b c исполнился бы как DEL a b).

**Базы (6 законов)** о действиях, которые меняют базы целиком (`R.Act`), в момент 0:
- `focus_keeps` и `focus_on` — SELECT не меняет ни одной базы и ставит в фокус ту,
  которую назвал, если она есть;
- `swap_dbs` — SWAPDB ставит каждую из двух баз на место другой;
- `wipe_dbs` — FLUSHALL опустошает все базы;
- `move_key` — MOVE ключа, который есть, в другую базу, где его записи нет, убирает
  запись ключа из выбранной базы и ставит её, со значением и сроком, в ту;
- `copy_key` — COPY ключа, который есть, ставит его запись (значение и срок) целевому
  ключу в базе, которую назвал (или в выбранной), если целевого ключа там нет или дан
  REPLACE, и больше ничего не меняет.

**Сессии (5 законов)** о `session.bend`:
- `run_gen` и `run_log_gen` — **как бы сервер ни разобрал пачку, он исполняет её как общий
  путь её команды по порядку**: быстрый путь (`exec_batch`, `log_batch`) для пачки из одних
  команд базы от готового клиента — тот же общий путь (`fast_eq`), с теми же ответами,
  состоянием соединения и сервера и базой;
- `gen_db` — пачка меняет базы ровно как действия команд, которые в ней исполнились
  (`S.plan`), так что законы команд и баз держатся и для них;
- `gen_log` — и пишет в журнал эффекты, которые им даёт `exec_log`: файл хранит историю
  исполненных команд, и законы персистентности держатся как есть;
- `noauth` — **клиент, который не вошёл, на сервере с паролем, до AUTH или HELLO
  исполняет на базе только ошибки разборщика**: он не может ни прочесть, ни изменить
  ни одного ключа.

**Конфигурация (3 закона)** о `config.bend`:
- `config_fail` — **CONFIG SET, который не удался, оставляет сервер как был** (Redis
  ставит параметры до сбойного и возвращает их назад, BendKV не ставит ни одного);
- `config_pass` — удавшийся оставляет сервер с новыми параметрами, и их `requirepass` —
  пароль с этого момента;
- `config_set_get` — **после удавшегося CONFIG SET параметра в нём лежит значение, которое
  дала его проверка, и CONFIG GET находит его по тому же имени** (поиск без учёта регистра,
  по имени или второму имени).

`bend proof/PROOF.bend` (`make check`) → `ALL PROOFS CHECK` (~4 с); `bend proof/PROOF.bend --verdict` → `ALL PROOFS CHECK`
(~40 с). Во втором случае каждое доказательство перепроверяет ядро BendTT, корректность
которого доказана в Lean. Трансляцию, которую читает ядро, можно выгрузить через
`bend proof/PROOF.bend -o PROOF.bendtt` и прочитать формулировки законов глазами.

  в том числе после `include`, `--save` без значения, вторые имена, кавычки и экранирование,
  `hz` вне пределов, единицы памяти, относительный `dir` и `include` после него,
  стандартный ввод), — те же значения CONFIG GET; 15 отказов самого BendKV и его
  собственное: `--version`, короткая форма, лог в файле, pid-файл, защищённый режим,
  два адреса с общей нумерацией клиентов.
- `tests/smoke.bend` — сквозной прогон «буфер → разбор → исполнение → RESP» без сети.
- **Числа на краях** (`tests/numbers_test.py`): каждой команде, которая берёт число,

  Тест нашёл, что `SELECT 9223372036854775807` останавливал сервер (раздел 28
  PERFORMANCE.md).
- **BITFIELD** (`tests/bitfield_test.py`): 3 000 случайных команд на трёх ключах — поля
  всех типов на смещениях до 256 бит или `#k`, значения на краях полей и long long, все
  виды переполнения; после каждой читается значение ключа. Ответы и значения — как у
  Redis.
- **Многие клиенты.** `make test` гоняет устойчивость и дифференциальный тест с
  писателем и без него. `tests/concurrency_test.py` проверяет при многих клиентах три
  вещи: INCR не теряются, MSET шестнадцати ключей атомарен для MGET, а порядок записей
  одного клиента в разные ключи виден другим так же, как в Redis.
- **Журнал.** `tests/aof_check.bend` пишет журнал пачки, читает и исполняет его и
  сверяет базу, а затем режет файл на каждой из его 2 310 длин и проверяет, что прочитанное
  и остаток вместе дают обрезок, а в остатке нет целой записи; то же — для журнала
  действий на нескольких базах (SELECT, SWAPDB, оба шага MOVE, COPY в том виде, как его
  пишет BendKV, и как его пишет Redis, FLUSHALL): базы после повтора те же, и каждый из
  1 251 его обрезка читается. `make test` гоняет весь
  набор и на сервере с журналом, а затем перезапускает его: случайный поток с FLUSHALL
  посередине (он ходит по базам, переносит ключи и меняет базы местами) плюс 20 тыс.
  ключей, перезапуск из файла, сравнение всего пространства ключей каждой из 16 баз
  (совпало: 20 237 ключей); дописанная обрезанная запись, перезапуск, который её
  отрезает, и снова то же пространство ключей. `tests/aof_fail_test.py` ломает диск под
  журналом прокладкой `tests/fail_io.c` (`LD_PRELOAD`): файл, который есть, но не
  читается, — отказ стартовать, файл не тронут; неудавшийся `fsync` при `everysec` и
  `always` — остановка. `redis-check-aof` из Redis 7 признаёт файлы BendKV корректными
  (с SELECT, SWAPDB, MOVE, COPY и FLUSHALL), Redis 7.0.15 загружает журнал BendKV и получает
  те же данные в тех же базах, а BendKV загружает журнал,
  записанный Redis (с `SELECT`, именами команд в нижнем регистре, уже переписанным в SET
  GETSET и COPY в том виде, как его прислал клиент). `tests/aof_redis_test.py` (в
  `make test`) проверяет это в обе стороны: те же команды идут в BendKV и в redis-server
  со своим журналом, затем BendKV стартует из файла Redis, а Redis — из файла BendKV, и
  каждый держит те же базы, что держал другой.

    переходов и с одним продолжением вместо шестнадцати; строка из одного куска как сам
    терм буфера, без узла; подсказка процессору `Mem.prefetch`; `IO` в прямых
    продолжениях (блок `do` вызывает эффекты прямо, без замыканий `IO.bind`);
  - в BendKV: ввод-вывод буферами; трай на 16 детей; чтение без разделения базы; разбор

    буфер; выбор команды по длине имени; разбор числа для INCR по индексу, без разборки
    строки; подсказки по пачке: пути всех ключей пачки загружаются уровень за уровнем до
    её исполнения.

### Граница доверия

Доказательства покрывают `map.bend`, `redis.bend`, `batch.bend`, `aof.bend`,
`session.bend`, `config.bend` и сами законы. На доверии остаются:
1. **Компилятор и рантайм Bend.** `U32` в теории — вектор из 32 битов (`Word(32n)`),
   в рантайме — машинное u32; `Nat` в теории унарный, в рантайме — 64-битное слово
   с аварийной остановкой после 2^48−1; `String` в теории — список, а в C-рантайме
   с патчем — цепочка байтовых буферов, а `String.eq`, `String.hash` и другие операции над
   ней — функции на C. Соответствие рантайма определениям не доказано. Сервер собирается
   Bend с двадцатью одним патчем из [`bend-patches/`](bend-patches/). Они тоже в доверенной
   базе: проверены набором тестов Bend и дифференциальными тестами против Redis, но не
   доказаны. Сюда же относятся циклы событий на нескольких потоках, `epoll`, атомарность
   `Chan.send_all`, поток-писатель и отправки, которые цикл делит с ним, файловые
   `write`/`read`/`fdatasync`/`ftruncate`, `Chan.drain`, нативные `String.dec_line_at` и
   `hash_at`, перевод `IO` в продолжения и раскладка записей шире 32 слов отдельным узлом
   в компиляторе. На доверии и перевод программы
   на Bend в язык ядра BendTT: само ядро доказано в Lean, перевод — нет. После выхода
   Bend 2 нашли несколько ошибок, при которых `--verdict` проходит, а ядро проверило не
   то, что написано в исходнике ([#1186](https://github.com/bendlang/bend/issues/1186),
   [#1236](https://github.com/bendlang/bend/issues/1236),
   [#1247](https://github.com/bendlang/bend/issues/1247), открыты на октябрь 2026). Их
   условий в доказательствах BendKV нет (нет специализированных параметров пустых типов,
   хелперов законов с именами конструкторов Base и столкновений имён через двоеточие и
   точку), но перевод остаётся в доверенной базе.
2. **`resp.bend`, `info.bend`, `server.bend` и `startup.bend`** — протокол, INFO, сеть
   и запуск; они проверены только тестами (запуск — против `redis-server`,
   `tests/start_test.py`, INFO — `tests/info_test.py`).
   С журналом на доверии и то, что сервер дописывает в файл именно эффекты каждой пачки
   (группа пачек пишется одной записью: `encode` склейки — склейка `encode`, это
   доказано в `enc_cat`). Когда файл кончается посреди записи, доказано, какую базу
   сервер поднимает и до какого байта режет файл (`recover_cut`, `load_cut`); на
   доверии лишь решение резать: что остаток — начало записи, а не мусор, сервер узнаёт
   сетевым разбором `resp.bend` (`cut_short`). Для оборванного файла ошибка там может
   только помешать старту, но не изменить базу. Определения `server.bend` с бесконечными
   циклами помечены `@unsafe` и честно стоят вне гарантий.
3. **clang, libc, ОС.**
4. **Ресурсные пределы** — вне логики Bend. Переполнение `Nat` предотвращено конструктивно:
   целые ≤14 цифр, длины ≤10 цифр, топливо парсера — 2^32−1 (запрос не короче 4 байт).
   Но это аргумент, а не доказанный закон. Исчерпание кучи — аварийная остановка.

## Ограничения Bend2, выявленные на практике

- **Нет `match` по вычисленному значению и по let-переменной; рекурсия только структурная,
  без взаимной; функцию можно вызвать только выше по файлу.** Forward-declaration через
  `law` разрешена лишь Base. Приходится выносить ветвления во вспомогательные функции,
  а аргументы вычисляются строго — отсюда «жадные» вычисления (см. `bget`, `bdel`) и
  топливо в парсере. В KEYS это стоило дорого: прежний `glob` считал обе ветви `Bool.or`
  для каждой `*`, то есть перебирал все разбиения ключа даже для шаблона, который
  совпадал сразу (а шаблон `a*a*…a*b`, который не совпадает нигде, без отсечки Redis
  подвешивал сервер на минуты — это нашёл набор тестов Redis); теперь KEYS сопоставляет
  как `stringmatchlen` Redis, одной функцией с явным режимом и отсечкой.
- **Аффинность.** Функция-гипотеза (`∀k. …` или опровержение `a != b`) используется один раз,
  а равенства — это `Data`, и их можно копировать. Поэтому опровержения переводятся в
  равенства булевых вердиктов (`{False == str_eq(j,k)}`). По той же причине
  доказательства уточнения относительно эталонной модели с ∀-инвариантом неудобны.
  Мы доказали законы напрямую. Законы журнала поэтому сформулированы от старта сервера,
  для любой истории пачек, а нужные свойства истории выводит заново функция верхнего
  уровня, которую можно вызывать сколько угодно.
- **`case other` в доказательстве не уточняет цель.** В функции `case other` покрывает
  оставшиеся конструкторы, а в доказательстве переменная остаётся абстрактной («`c`, но не
  `Get`»), и функции от неё не редуцируются. Леммы о командах поэтому перечисляют все 19
  конструкторов, большую часть — опровержениями. Поэтому команды соединения собраны в
  одну команду `Own`, а чтения одного ключа — в `Peek`: каждая группа — один конструктор
  в этих леммах, сколько бы команд в ней ни было.
- **Чекер вычисляет `Nat` в унарной форме.** Константа вроде 10^14 переполняет стек
  чекера, поэтому проверка переполнения в INCR сделана по числу цифр.
- **Нет тактик и автоматизации.** Каждый шаг переписывания пишется руками, с явным мотивом.
  Доказательств получилось примерно столько же, сколько кода, — для ручного режима это
  неплохо. Проверка же действительно быстрая.
- **`match` идёт до локальных привязок, а разбор пары — только переменной.** `match x` после
  `%rewrite` или `+y = …` в том же теле не принимается; разбирать вложенную пару
  `(a, (b, c))` в одном теле чекер не умеет вывести — второй уровень уходит в отдельную
  функцию. Зато есть образцы `case 10n+m` и `case 1n++p` (дублируемая переменная), что
  и позволило делить на 10 «шагами по десять».
- **Представление данных:** в стоковом Bend строки — связные списки (патч упаковывает их
  в C-рантайме, см. PERFORMANCE.md), нет 64-битных чисел, мало эффектов (в стоке ввод-вывод
  файлов без `fsync`; двенадцатый патч добавляет его). Для СУБД это главный практический
  блокер.

## Как запустить

И доказательствам, и серверу нужен Bend с патчами: сервер использует
`TCP.recv_raw`/`TCP.send_raw` из второго патча, а карта хеширует ключи `String.hash`,
которое четвёртый патч добавляет в Base, подсказывает процессору `Mem.prefetch` из
девятого, поток-писатель (`TCP.post`) и `Chan.send_all` берёт из десятого, а журнал —
`File.write_raw`, `read_raw`, `sync` и `truncate` из двенадцатого и `Chan.drain` из
тринадцатого. Разборщик читает строки чисел и хеши ключей по индексу функциями из
семнадцатого. Запуск меняет каталог и пишет в лог pid и дату функциями двадцатого
(`IO.chdir`, `IO.cwd`, `IO.pid`, `IO.clock`); ими же INFO знает pid и время. Остальные
только ускоряют рантайм и код.
Makefile передаёт Bend `CC=clang-19`, если такой есть: clang 18 игнорирует соглашение
`preserve_none`, и код выходит на ~8% медленнее.

```bash
# Bend с патчами: клон bendlang/bend, на него двадцать один патч из bend-patches/;
# для --verdict нужен Lean 4.34.0 (elan)
git clone https://github.com/bendlang/bend ../bend-patched
sh bend-patches/apply.sh ../bend-patched
B="bun ../bend-patched/bend2/main.ts"
make check BEND="$B"     # доказательства
make verdict BEND="$B"   # доказательства + перепроверка ядром BendTT (первый раз собирает ядро ~40 с)
make build BEND="$B"   # нативный сервер build/bendkv (clang, ~40 с)
make run               # ./build/bendkv 6380 (./build/bendkv 6380 post — с потоком-писателем,
                       # ./build/bendkv 6380 send — без писателя,
                       # ./build/bendkv 6380 post data.aof always — с журналом;
                       # как redis-server: ./build/bendkv redis.conf --port 7777)
redis-cli -p 6380 set foo bar
make test BEND="$B"    # запуск (около сотни командных строк и файлов на обоих серверах),
                       # устойчивость, дифференциальный тест против redis-server и
                       # согласованность при многих клиентах: по умолчанию, с писателем,
                       # без него, с журналом; края протокола, команды соединения, CONFIG,
                       # INFO и COMMAND против Redis; перезапуск из журнала и обрезанный хвост;
                       # отказы диска под журналом (нужен компилятор C)
make pgo BEND="$B"     # build/bendkv-pgo: сборка с профилем (нужен llvm-profdata)
make bench BEND="$B"   # redis-benchmark: BendKV против Redis
make suite BEND="$B" REDIS_SRC=../redis   # набор тестов Redis на Redis и на BendKV
                       # (дерево исходников Redis 7.0.15 с tests/, tclsh)
```

   модули, ACL сложнее пароля. Сделано: края протокола, команды соединения (сессии с
   законами), CONFIG по полной таблице параметров Redis (с законами), INFO с секциями
   и полями Redis, COMMAND с описаниями команд от самого Redis, статистика по командам
   в INFO (commandstats, errorstats), SCAN и RANDOMKEY, сроки жизни ключей (EXPIRE и
   его родня, TTL, опции SET, GETEX, GETDEL — с законами и восстановлением из журнала с
   временами), чистка истёкших ключей, несколько баз (SELECT, MOVE, SWAPDB, FLUSHDB,
   FLUSHALL, строки keyspace по базам — с законами и восстановлением всех баз из
   журнала), диапазоны и биты строк (GETRANGE, SETRANGE, GETBIT, SETBIT, BITCOUNT, BITPOS
   — с законом SETRANGE и восстановлением из журнала). Набор Redis во внешнем режиме:
   BendKV проходит 424 из 1 673 тестов, которые проходит сам Redis, и 401 из 689 в юнитах
   того, что в нём есть
   ([docs/COMPATIBILITY.md](docs/COMPATIBILITY.md)); больше всего тестов стоит на типах
   данных (547) и RESP3 (на HELLO 3 останавливается и `unit/type/list`, за 203 тестами
   до конца). Запуск —
   как у redis-server (командная строка и файл конфигурации). База — запись со счётчиком
   ключей (DBSIZE за O(1)). TOUCH, TIME и OBJECT. MSETNX, RENAME и RENAMENX — с
   законами, коммутативностью для команд, чьи записи зависят от других ключей, и
   восстановлением из журнала. COPY (в выбранную базу или в другую) — с законом и
   восстановлением из журнала, который читает и COPY, как его пишет Redis. BITOP — с
   законом и законами коммутативности; LCS. BITFIELD и BITFIELD_RO — поля до 64 бит
   (слова из двух половин U32) с записью как SETRANGE байтов, до которых дошли записи.
   Значение — строка или коллекция, с ошибкой WRONGTYPE, как у Redis, для команды не того
   типа (основа для типов; цена — узел на значение, раздел 31 PERFORMANCE.md). Хеши
   (HSET и его родня, HINCRBY, HSCAN, HRANDFIELD; MEMORY USAGE) — малый хеш в порядке
   прихода полей, большой в своём трае, как listpack и hashtable у Redis; в журнал —
   HSET и HDEL, а хеш поверх истёкшего ключа — одной записью EVAL постоянного скрипта
   (законы журнала требуют одной записи на действие; Redis пишет тут MULTI из двух).
   Списки (LPUSH и его родня, LPOP/RPOP со счётчиком, LINDEX, LRANGE, LSET, LINSERT,
   LREM, LTRIM, LPOS, LMOVE, RPOPLPUSH, LMPOP) — дек из двух стеков; LMOVE и LMPOP — с
   законами коммутативности для команд над несколькими ключами; в журнал — сама запись,
   а перенос на истёкший ключ — одной записью EVAL постоянного скрипта. Следующий шаг —
   множества.
2. **Журнал дальше.** Перезапись журнала (BGREWRITEAOF): снимок базы командами SET с
   законом, что он читается так же, как база (по ключам, а не по форме трая). Закон о
   продолжении: после обрезки и новых записей файл — журнал истории «префикс + новые
   пачки». И закон обратимости сетевого разбора `resp.bend`: формат журнала — те же
   массивы bulk-строк, что шлют клиенты, и он же доказал бы решение резать оборванный
   файл (`cut_short`).
3. **Законы для новых типов.** Законы коммутативности уже обобщены на команды, чьи
   записи зависят от других ключей (RENAME, MSETNX, BITOP, LMOVE, LMPOP); SUNIONSTORE и
   его родня лягут в ту же схему. Инвариант счётчика ключей
   (DBSIZE — размер трая) и закон полноты KEYS; тот же инвариант («в бакете нет повторов
   ключа») пустит DBSIZE в законы о перестановке.
4. **Производительность.** Время запроса теперь в основном системное: меньше
   системных вызовов на запрос (`io_uring`, ожидание нескольких готовых сокетов); буферы
   постов без `malloc` (~690 инструкций на запрос без конвейера); продолжение после
   эффекта — без узла задачи; разбор RESP дешевле ещё раз (~1 370 инструкций на GET с
   хешем); шарды (ветка [`archive/shards`](https://github.com/littleBro/BendKV/tree/archive/shards)) вернуть в готовый проект в следующем цикле
   оптимизации и проверить на машине, где серверу достаётся больше трёх ядер.
   Чередование чистых задач в рантайме на вероятных промахах: выигрыш подсказок без
   ручной пакетизации. PGO в драйвере Bend (в BendKV — `make pgo`), аппаратный хеш (ключ
   хешируется дважды: для подсказок и в `exec`), INCR за один проход по траю. Предложить
   патчи в `bendlang/bend` (снять регрессию на бенчмарке `lexer`, цену страниц по 2 МиБ
   для коротких программ и уложиться в потолок размера `comp.ts`; первым — ленивое
   запечатывание: лучшее соотношение выигрыша и цены, и оно помещается в запас до
   потолка; затем перевод `IO` в продолжения). См. [PERFORMANCE.md](docs/PERFORMANCE.md),
   разделы 7.14, 7.17, 7.23, 7.24, 9.6, 11 и 14.
5. **SQL-направление:** верифицированное B+-дерево в памяти, затем небольшой движок
   реляционной алгебры с законами корректности оптимизатора (по образцу
   `demos/proof_typed_eval`), и только потом — диск.
